# Правило безопасных миграций структуры БД и служебных промптов

> **ОБЯЗАТЕЛЬНОЕ ПРАВИЛО**: Если меняется база данных (DDL) или добавляются/изменяются служебные промпты, шаблоны и системные настройки в таблицах базы данных, ведущий агент («Руководитель проектов») и субагенты обязаны **всегда создавать план безопасных миграций на прод и применять его на продакшене так же, как и миграции изменения структуры БД**.

---

## 1. Область действия (Триггеры правила)

Правило активируется при ЛЮБОМ из следующих изменений:
1. **Структурные изменения БД (DDL)**:
   - Создание, модификация или удаление таблиц (`CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`).
   - Добавление колонок, внешних ключей (`FK`), ограничений (`constraints`).
   - Создание или изменение индексов (`CREATE INDEX`).
2. **Служебные промпты и функции AI**:
   - Добавление, обновление или калибровка записей в `HUNTTECH_AI_FUNCTION_CONFIGURATION` (системные промпты `system_prompt`, шаблоны `prompt_template`, политики маршрутизации, параметры температуры, токенов, квот).
   - Шаблоны вакансий и промптов `HUNTTECH_VACANCY_PROMPT_TEMPLATE`.
   - Конфигурации моделей и шлюзов `HUNTTECH_ADMIN_AI_CONFIGURATION`, `HUNTTECH_USER_AI_CONFIGURATION`.
3. **Системные данные, права и справочники**:
   - Назначение специфических прав доступа (`SEC_PERMISSION`), ролей и экранов.
   - Корпоративные календари, интеграции Yandex 360, дефолтные профили пользователей.

---

## 2. Стандарт оформления миграций (Единый источник истины)

1. **Канонический каталог CUBA SQL**:
   - Все миграции обязаны сохраняться в `modules/core/db/update/postgres/26/` в виде чистых SQL-скриптов с префиксом даты: `YYMMDD-N-description.sql`.
2. **Интеграция с Liquibase (без дублирования)**:
   - Если создаётся Liquibase XML-файл в `modules/core/db/changelog/`, он **НЕ ДОЛЖЕН** дублировать SQL или текст промптов внутри себя.
   - Обязательно использовать ссылку на канонический файл через `<sqlFile>`:
     ```xml
     <changeSet id="YYMMDD-N-name" author="hunttech">
         <sqlFile path="../update/postgres/26/YYMMDD-N-name.sql"
                  relativeToChangelogFile="true"
                  splitStatements="true"/>
     </changeSet>
     ```
3. **Защитные условия (WHERE-guards) для промптов**:
   - Обновления промптов (`UPDATE`) обязаны содержать защитные фильтры:
     - `DELETE_TS IS NULL` (не трогать удалённые).
     - Проверка `CONFIGURATION_VERSION` (не затирать более новые версии).
     - Защита ручных правок администратора (`CREATED_BY = 'migration' AND COALESCE(UPDATED_BY, 'migration') = 'migration'`).

## 3. Регламент безопасного деплоя миграций на прод

При любом релизе или деплое изменений, затрагивающих БД или служебные промпты:

### Шаг 1. Формирование плана миграции (Safe Migration Plan)
Зафиксировать в чекпоинте/отчёте:
- Список применяемых SQL-скриптов.
- Ожидаемые изменения данных (количество строк, добавленные таблицы).
- План отката (Rollback).

### Шаг 2. Обязательный бэкап данных (Data Safety First)
**ПРЕЖДЕ чем применять любые миграции на прод, ОБЯЗАТЕЛЬНО создаётся полный дамп БД**:
```bash
BACKUP_DIR=/opt/backups/deploy_$(date +%Y%m%d_%H%M%S)
mkdir -p $BACKUP_DIR
PGPASSWORD=cuba pg_dump -U cuba -h localhost -Fc hunttech > $BACKUP_DIR/hunttech_pre_migration.dump
```

### Шаг 3. Транзакционное применение миграций
- Миграции на продакшене выполняются строго в единой транзакции с флагом `ON_ERROR_STOP=1`:
```sql
BEGIN;
\i /tmp/YYMMDD-1-table.sql
\i /tmp/YYMMDD-2-prompts.sql

INSERT INTO sys_db_changelog (script_name, create_ts, is_init)
VALUES
('70-hunttech_recruiting/update/postgres/26/YYMMDD-1-table.sql', CURRENT_TIMESTAMP, 0),
('70-hunttech_recruiting/update/postgres/26/YYMMDD-2-prompts.sql', CURRENT_TIMESTAMP, 0)
ON CONFLICT DO NOTHING;

COMMIT;
```

### Шаг 4. Обязательная регистрация в `sys_db_changelog`
- Каждый применённый на проде скрипт фиксируется в `sys_db_changelog`, чтобы локальный и прод-механизм CUBA `CubaDbUpdate` не пытался применить его повторно.

### Шаг 5. Автоматическая сверка (Deep Diff Validation)
- Выполнить глубокую поколоночную сверку между локальной БД и базой продакшена.
- Убедиться, что:
  - Все новые таблицы и индексы присутствуют на проде.
  - Количество и содержимое записей служебных промптов в `HUNTTECH_AI_FUNCTION_CONFIGURATION` совпадает на 100%.

---

## 4. Контроль Definition of Done
Задача по изменению БД или служебных промптов считается завершённой **ТОЛЬКО ПОСЛЕ ТОГО**, как:
1. Созданы и закоммичены парные `.sql` скрипты в `db/update/postgres/26/`.
2. Скрипты проверены и применены локально (`agent-gradle.sh updateDb`).
3. Выполнен бэкап продакшена.
4. План миграции применён на продакшене, скрипты зарегистрированы в `sys_db_changelog`.
5. Результат проверен глубоким diff между локальной базой и продом (100% идентичность).
