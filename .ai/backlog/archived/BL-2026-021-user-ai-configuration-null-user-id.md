## Исходная мысль руководителя

> Новая ошибка: PSQLException: ERROR: null value in column "user_id" violates not-null constraint
> Подробности: Failing row contains (..., alan, ..., null, ..., deepseek, ..., deepseek-v4-flash, t, ..., f, 3, 10, 10000).
> СРОЧНО

## Проблема

При сохранении новой записи `com.company.hunttech.entity.UserAiConfiguration` приложение выполняет `INSERT` в `HUNTTECH_USER_AI_CONFIGURATION`, передавая `USER_ID = NULL`. PostgreSQL отклоняет запись ограничением `USER_ID NOT NULL`.

Из приложенного stack trace подтверждено:

- SQL: `INSERT INTO HUNTTECH_USER_AI_CONFIGURATION (..., PROVIDER_CODE, ..., DEFAULT_MODEL_NAME, ..., USER_ID)`;
- сущность: `UserAiConfiguration`;
- пользователь приложения в аудите: `alan`;
- провайдер: `deepseek`;
- модель: `deepseek-v4-flash`;
- запись новая (`InsertObjectQuery`), активная, с зашифрованным секретом;
- значение `USER_ID` в bind-параметрах равно `null`.

Секрет/API-ключ из диагностического сообщения намеренно не сохраняется в backlog и не должен попадать в обычные логи.

## Что проверено в коде и документации

### Подтверждённая модель данных

- [UserAiConfiguration.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/global/src/com/company/hunttech/entity/UserAiConfiguration.java) объявляет обязательную связь `@ManyToOne(optional = false)` с `com.haulmont.cuba.security.entity.User` через `@JoinColumn(name = "USER_ID")`.
- [260727-2-reconcileProductionSchema.sql](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/core/db/update/postgres/26/260727-2-reconcileProductionSchema.sql) создаёт `HUNTTECH_USER_AI_CONFIGURATION.USER_ID UUID NOT NULL`, проверяет строки без владельца и добавляет внешний ключ на `SEC_USER(ID)`.

### Предусмотренный пользовательский сценарий

- [UserAiConfiguration.md](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/docs/entities/user-ai-configuration/UserAiConfiguration.md) описывает персональные ключи и модели пользователя; редактирование выполняется через вкладку «Персональный ИИ» в `sec$User.edit` и модальное окно `hunttech_UserAiConfiguration.edit`.
- Документ прямо фиксирует, что `UserAiConfigurationEdit` должен автоматически привязывать `user` из родительского `ExtUser`.
- [UserAiConfigurationEdit.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/web/src/com/company/hunttech/web/screens/useraiconfiguration/UserAiConfigurationEdit.java) устанавливает владельца из `parentUser` в `onInitEntity` и повторно в `onBeforeShow` для новой сущности.
- [ExtUserEdit.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/web/src/com/company/hunttech/web/screens/extuser/ExtUserEdit.java) при создании конфигурации передаёт пользователя через `withInitializer(entity -> entity.setUser(user))`.

### Рабочая гипотеза

Текущая реализация содержит защиту в основном пути `ExtUserEdit`, поэтому ошибка, вероятно, возникает в одном из следующих случаев:

1. существует другой путь открытия `UserAiConfigurationEdit` или REST/сервисный путь, где владелец не задаётся;
2. в рабочей среде запущена версия до текущей автопривязки;
3. параметр `parentUser` не передаётся либо теряется при создании модального редактора;
4. запись создаётся не из `ExtUserEdit`, а из административного/пользовательского экрана с пустым `user`.

Гипотезу нельзя считать подтверждённой без воспроизведения и проверки SHA развёрнутой версии.

## Ожидаемый результат

Новая персональная AI-конфигурация сохраняется только с валидным владельцем `SEC_USER.ID`. При отсутствии владельца пользователь получает понятное сообщение в форме, а попытка записи в БД не выполняется. Конфигурация DeepSeek и другие провайдеры должны сохраняться и редактироваться без нарушения ограничения.

## План срочного расследования и исправления

1. Зафиксировать `BASE_SHA` текущего репозитория и SHA рабочей среды; сопоставить их с приложенным временем ошибки.
2. Воспроизвести сохранение конфигурации DeepSeek под `alan` в каждом доступном пути: `ExtUserEdit`, пользовательские настройки и административный мониторинг. В production выполнять только чтение и проверку логов, без исправляющих SQL-записей.
3. Найти все вызовы `UserAiConfigurationEdit` и все сервисные/REST-операции создания `UserAiConfiguration`; построить карту, где назначается `user`.
4. Исправить корневой путь: передавать владельца при создании и повторно валидировать его перед commit. Не подставлять владельца по `createdBy` автоматически без явного правила: `createdBy` — строка аудита, а `USER_ID` — FK на `SEC_USER`.
5. Добавить проверку на UI/service-уровне до сохранения и безопасное сообщение об отсутствии владельца; сохранить текущую защиту `USER_ID NOT NULL` и внешний ключ.
6. Проверить редактирование существующей записи, переключение провайдера, повторное сохранение, флаг primary и шифрование секрета. Секрет не выводить в логи и отчёты.
7. Проверить наличие уже созданных некорректных строк read-only запросом. Автоматическое назначение владельца и исправляющую миграцию выполнять только после определения владельца и отдельного решения.
8. Синхронизировать документацию сущности и сценария создания; добавить тесты на каждый путь создания и на запрет commit без `user`.

## Предварительные критерии готовности

- сохранение новой конфигурации DeepSeek под `alan` завершается успешно;
- в сохранённой строке `HUNTTECH_USER_AI_CONFIGURATION.USER_ID` заполнен и ссылается на правильную запись `SEC_USER`;
- ни один поддерживаемый путь создания не вызывает INSERT с `USER_ID = NULL`;
- при программно или UI созданной сущности без владельца commit блокируется понятным сообщением;
- редактирование и повторное сохранение не меняют владельца ошибочно;
- ключ хранится только в зашифрованном поле, plaintext не попадает в SQL-логи/backlog;
- проверены регрессии AI-функций, использующих пользовательскую конфигурацию.

## Открытые вопросы и допущения

- Вопрос: на какой форме или операции пользователь получил ошибку — вкладка `ExtUserEdit`, личные настройки, мониторинг ключей или другой путь?
- Вопрос: какой SHA и окружение соответствуют stack trace?
- Вопрос: есть ли на рабочем стенде несколько активных веток/контейнеров, чтобы исключить расхождение версии?
- Допущение: `alan` — пользователь аудита (`CREATED_BY`), а не доказанный владелец записи; по нему нельзя автоматически восстанавливать `USER_ID`.
- Допущение: сбой блокирует сохранение подключения, но не подтверждает сам по себе причины карточек BL-2026-016 или BL-2026-020.
