## Проблема и бизнес-сценарий

Внешнее приложение должно передавать в HRM комплект данных кандидата: основную карточку, одно или несколько резюме и взаимодействия по вакансиям. Система должна сохранить связи и вернуть внешний результат с ID созданных объектов, не создавая дубли при повторной доставке.

## Предлагаемый целевой контракт для аналитики

Предварительно нужен versioned application endpoint, например `POST /api/integrations/v1/candidates`:

- вход содержит `externalRequestId`/idempotency key, внешний ID кандидата, данные карточки, массив CV и массив взаимодействий;
- каждое CV связывается с кандидатом и при необходимости с существующей вакансией/должностью;
- каждое взаимодействие связывается с кандидатом, существующей вакансией и допустимым пользователем-рекрутером; нельзя принимать произвольный `RECRUTIER_ID` без проверки прав;
- файлы передаются по отдельному безопасному контракту (multipart или предварительно загруженный file token), без включения секретов и без предположения, что текущий FileStorage уже BLOB-хранилище;
- ответ возвращает IDs кандидата, CV и взаимодействий, статус операции и correlation ID;
- повтор с тем же idempotency key идемпотентен; повтор с тем же внешним ID обрабатывается по согласованной политике `reuse/update/reject`;
- при пакетной операции ошибка в обязательной связи или валидации не оставляет частично созданный комплект, либо API явно поддерживает режим частичного результата с отдельным контрактом.

Конкретный endpoint, DTO, порядок создания, дедупликация и режим частичной обработки должны быть утверждены аналитикой.

## Ожидаемый результат

Авторизованный внешний клиент создаёт или безопасно переиспользует карточку кандидата, сохраняет связанные резюме и взаимодействия, а HRM получает целостный граф данных: `JobCandidate → CandidateCV` и `JobCandidate → IteractionList → OpenPosition/ExtUser`.

## Предварительные критерии готовности

- внешний клиент может создать кандидата и получить его стабильный внешний/внутренний ID;
- одно или несколько резюме сохраняются с обязательной связью на кандидата;
- взаимодействия сохраняются только с валидными вакансией и рекрутером;
- повтор доставки не создаёт дубликаты согласно утверждённой политике;
- невалидный пакет не оставляет orphan CV/interaction или возвращает согласованный частичный результат;
- файлы и текст CV ограничены по размеру/типу и не раскрываются в логах;
- права внешнего клиента ограничены выделенным scope и не позволяют произвольный доступ к другим данным;
- существующий UI и умная загрузка кандидата продолжают работать без изменения бизнес-правил;
- API, сервис и миграции/индексы при необходимости покрыты тестами и документированы.

## Реализованный результат

Метод `POST /hrm/rest/v2/services/hunttech_ExternalIntegrationService/createCandidateWithDetails` полностью реализован, задеплоен и протестирован:
1. **Комплексное создание**: атомарное создание карточки кандидата (`JobCandidate`), его резюме (`CandidateCV`) и этапа взаимодействия (`IteractionList`) по вакансии в единой транзакции.
2. **Дедупликация кандидатов**:
   - Автоматический поиск существующего кандидата по телефону, мобильному телефону или email.
   - При совпадении карточка не дублируется (`status: EXISTING_FOUND`), недостающие реквизиты аккуратно обогащаются, создается новое резюме и взаимодействие.
3. **Data View Integrity**: использование специализированных представлений (`jobCandidate-dedup-view`, `openPosition-view`), предотвращающее ошибки `UnfetchedAttributeException`.
4. **Идемпотентность**: поддержка заголовка/поля `idempotencyKey` с in-memory кэшированием ответов.
