## Исходная мысль руководителя

> надо сделать API чтобы была возможность создания вакансии внешними приложениями.
> Надо создавать проект, вакансию.

## Проблема и бизнес-сценарий

Внешнее приложение должно отправить данные в HRM и получить созданные сущности проекта и вакансии. Операция должна сохранить связь `OpenPosition.projectName → Project`, чтобы вакансия была сразу пригодна для дальнейшей работы рекрутера, публикации и AI-сценариев.

## Что проверено в проекте

### Текущий REST-контур

- [web-app.properties](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/web/src/com/company/hunttech/web-app.properties) включает CUBA REST API v2 по контексту `/api`, OAuth2 password/refresh_token, закрытый anonymous-доступ и `GENERIC_UI` security scope.
- [rest-queries.xml](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/web/src/com/company/hunttech/rest-queries.xml) сейчас содержит в основном read-сценарии: публичные/все вакансии и справочники `Project`, `City`, `Position`, `Grade`. Разрешённого бизнес-сценария создания проекта и вакансии в документе нет.
- Поэтому задача требует спроектировать безопасный write-контракт, а не просто открыть общий CRUD для всех полей сущностей.

### Сущности и обязательная связь

- [Project.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/global/src/com/company/hunttech/entity/Project.java) хранит имя, описание, владельца, департамент, даты, закрытость и другие настройки; вакансии связаны с проектом через композицию `Project.openPosition`.
- [OpenPosition.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/global/src/com/company/hunttech/entity/OpenPosition.java) требует `vacansyName`, `remoteWork`, `commandCandidate`, `workExperience`, `internalProject` и обязательный `projectName` (`PROJECT_NAME_ID`). В сущности есть дополнительные ссылки на `Position`, `Grade`, `City`, `ExtUser owner`, описание, зарплатные и AI-поля.
- Существующая UI-документация [ProjectEdit_Spec.md](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/docs/ui/ProjectEdit_Spec.md) и [OpenPositionEdit_Spec.md](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/docs/ui/OpenPositionEdit_Spec.md) описывает каскады, обязательность и бизнес-правила экранов. API должен использовать те же правила, но не имитировать UI и не принимать неподходящие внутренние поля без решения владельца.

## Предлагаемый целевой контракт для аналитики

Предварительно нужен отдельный endpoint/сервис, например `POST /api/integrations/v1/projects-with-vacancies` или эквивалентный versioned route:

- вход: внешний `externalRequestId`/idempotency key, данные проекта, данные вакансии и явные ссылки на существующие справочники;
- результат: HTTP-статус, IDs и безопасное представление созданных `Project`/`OpenPosition`, без секретов и лишних внутренних полей;
- создание проекта и вакансии — одна транзакция: если вакансия не проходит валидацию, проект не остаётся сиротой;
- повтор запроса с тем же idempotency key не создаёт дубликаты и возвращает ранее созданный результат;
- связь вакансии с новым проектом устанавливается до commit;
- аудит хранит внешний клиент, время, correlation ID и результат без полного payload с чувствительными данными.

Конкретный URL, DTO, набор полей, правила поиска существующего проекта и режим «создать новый/использовать существующий» должны быть утверждены после ответов на открытые вопросы.

## Ожидаемый результат

Внешнее приложение авторизуется выделенным клиентом, отправляет валидный запрос и получает созданные проект и связанную вакансию. Ошибки аутентификации, прав, справочников, обязательных полей и дубликатов возвращаются в стабильном формате без частично сохранённых данных.

## Предварительный план проработки

1. Согласовать внешний сценарий и владельца API: источник, частоту, объём, допустимые поля и нужен ли только create или также update/status.
2. Провести аналитику обязательных полей `Project`/`OpenPosition`, значений enum/справочников и правил UI, включая проект, компанию, департамент, владельца, город, должность и режим открытия.
3. Выбрать архитектуру: application service в core + узкие DTO/mapper + versioned REST facade; не давать внешнему приложению произвольный generic entity CRUD.
4. Спроектировать OAuth2 client/roles, scope, rate limit, idempotency, correlation ID, аудит и защиту от массового создания.
5. Реализовать транзакционное создание проекта и вакансии с валидацией и понятными ошибками.
6. Добавить контрактные тесты: успешное создание, повтор запроса, неверный справочник, отсутствующее обязательное поле, отсутствие прав, rollback при ошибке вакансии.
7. Документировать API с примерами без реальных ключей, схемой версий и правилами миграции контракта.

## Предварительные критерии готовности

- внешний авторизованный клиент может создать проект и связанную вакансию одним согласованным API-сценарием;
- `OpenPosition.projectName` указывает на созданный или явно выбранный проект;
- невалидный запрос не оставляет частично созданный проект;
- повтор с тем же idempotency key идемпотентен;
- доступ к endpoint ограничен выделенной ролью/scope;
- ответ не раскрывает API-ключи, внутренние секреты и лишние поля;
- ошибки имеют стабильные коды и correlation ID;
- существующие UI-сценарии создания/редактирования проекта и вакансии не изменены;
- API и сервис покрыты тестами и опубликована актуальная документация.

## Открытые вопросы и допущения

- Вопрос: какое внешнее приложение будет первым клиентом и нужен ли ему только create или также update/close вакансии?
- Вопрос: проект всегда создаётся новым или API должно уметь находить/переиспользовать существующий проект по внешнему ID/коду?
- Вопрос: какие поля проекта и вакансии приходят извне; кто задаёт обязательные значения `remoteWork`, `commandCandidate`, `workExperience`, `internalProject`, владельца и компании?
- Вопрос: нужно ли сразу открывать вакансию (`openClose`) или создавать черновик для проверки рекрутером?
- Вопрос: требуется ли принимать исходное описание вакансии и запускать AI-подготовку/извлечение навыков асинхронно?
- Вопрос: какой протокол авторизации, лимит запросов, SLA и формат ошибок нужны внешнему приложению?
- Допущение: операция создания проекта и вакансии должна быть атомарной и не должна обходить существующие права и валидации.
