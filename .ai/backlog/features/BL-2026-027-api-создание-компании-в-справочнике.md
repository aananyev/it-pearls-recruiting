## Проблема и бизнес-сценарий

Внешнее приложение должно передать организацию в HRM и получить созданную запись справочника `Company`. Компания должна стать доступной для выбора в проекте, вакансии, карточке кандидата и других связанных сущностях без ручного дублирования данных.

## Что проверено в проекте

### REST-контур

- [web-app.properties](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/web/src/com/company/hunttech/web-app.properties) включает CUBA REST API v2 на `/api`, OAuth2 password/refresh_token, закрытый anonymous-доступ и `GENERIC_UI` security scope.
- [rest-queries.xml](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/web/src/com/company/hunttech/rest-queries.xml) содержит read-запрос `company` пока только косвенно через справочники/связанные сценарии; отдельного write-контракта создания `Company` нет. Generic CRUD не должен открываться внешнему приложению без ограничения полей и прав.

### Модель `Company`

- [Company.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/global/src/com/company/hunttech/entity/Company.java) имеет обязательное поле `comanyName` (историческая опечатка в имени свойства/колонки), а также короткое название, юридическое имя, ИНН, КПП, ОГРН, ОКПО, ОКТМО, ОКВЭД, адреса, банк, телефон, email, сайт и признаки клиента/юрлица.
- Сущность связывается с `CompanyGroup`, директором `Person`, городом, регионом, страной, логотипом и коллекцией `CompanyDepartament`. Эти ссылки должны приниматься как проверенные ID/внешние ключи, а не как произвольные строки без правил резолвинга.
- [company-edit.xml](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/web/src/com/company/hunttech/web/screens/company/company-edit.xml) показывает, что UI поддерживает реквизиты, адреса, контакты, логотип и структурные связи. API должен отделить минимально обязательные поля от необязательных и не имитировать все UI-кнопки автоматически.
- В экране есть «Умная загрузка реквизитов», которая ищет данные по названию/ИНН и предупреждает о найденной компании-дубликате. Этот сценарий подтверждает необходимость явной политики дублей, но не заменяет интеграционный API.

## Предлагаемый целевой контракт для аналитики

Предварительно нужен versioned endpoint, например `POST /api/integrations/v1/companies`:

- вход: внешний ID и idempotency key, наименование, реквизиты и согласованные ссылки на справочники;
- результат: ID/внешний ID компании, нормализованное наименование, статус `created`/`existing` и correlation ID;
- повтор с тем же ключом не создаёт дубль;
- при совпадении ИНН/ОГРН/внешнего ID API действует по утверждённой политике `reuse`, `update` или `reject`, без неявного слияния;
- логотип и файлы передаются отдельным безопасным механизмом, с лимитами и MIME-проверкой; будущую BLOB-стратегию из BL-2026-001 не считать автоматически частью этой задачи;
- ошибки валидации, прав, справочников и конфликтов возвращаются стабильным форматом без секретов и лишнего персонального payload.

## Ожидаемый результат

Авторизованный внешний клиент может создать или безопасно переиспользовать компанию в справочнике. Запись валидна для выбора в других формах, а повторная доставка данных предсказуемо обрабатывает дубликаты.

## Предварительный план проработки

1. Согласовать внешний источник, внешний ID, объём и частоту передачи компаний.
2. Описать обязательное `comanyName`, правила нормализации названия и валидации ИНН/КПП/ОГРН.
3. Определить, можно ли создавать или изменять `CompanyDepartament`, директора, группу и адресные справочники в том же запросе.
4. Спроектировать application service + DTO + mapper и транзакционные проверки; generic entity CRUD не использовать как публичный бизнес-контракт.
5. Ввести OAuth2 client/role/scope, rate limit, idempotency, correlation ID и аудит.
6. Решить политику логотипа и файлов, не раскрывая содержимое и ключи в логах.
7. Добавить тесты успешного создания, дублей, неверных реквизитов/справочников, повторного запроса, отсутствия прав и безопасной ошибки.
8. Опубликовать versioned API-документацию с примерами без реальных идентификаторов и секретов.

## Предварительные критерии готовности

- внешний клиент создаёт валидную запись `Company` через выделенный API;
- обязательное наименование и формат реквизитов проверяются до commit;
- компания доступна в существующих picker/lookup и связях проекта, вакансии и кандидата;
- повтор запроса идемпотентен;
- политика дублей по внешнему ID/ИНН/ОГРН документирована и протестирована;
- endpoint ограничен выделенным scope/ролью и не раскрывает лишние поля;
- существующие UI и «Умная загрузка реквизитов» продолжают работать;
- опубликована документация и добавлены контрактные тесты.
