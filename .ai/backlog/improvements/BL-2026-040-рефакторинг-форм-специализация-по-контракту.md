## Исходная мысль руководителя

> На будущее: рефакторинг форм Edit и Browse "специализация" в соответствии с контрактом разработки форм Hunttech HRM

## Проблема

Требуется привести Edit- и Browse-экраны справочника «Специализация» к применимым обязательным UI-контрактам HRM HuntTech. Edit уже имеет двухпанельную композицию, sidebar, вкладки и штатные действия; Browse пока представляет собой простой список с фильтром и стандартной таблицей. Перед изменениями необходимо установить конкретные отклонения каждого экрана от нормативных документов, а не повторно переделывать уже соответствующие элементы.

## Ожидаемый результат

Оба экрана соответствуют применимым контрактам: Edit сохраняет согласованную композицию карточки специализации, а Browse получает контрактную компоновку и состояния либо документированное обоснование допустимого исключения для простого справочника. Сценарии создания, изменения, выбора специализации и просмотра связанных кандидатов остаются рабочими.

## Расследование документов, форм и необходимые действия

### Нормативные документы

1. **`docs/architecture/HRM_HuntTech_Edit_Screen_Shared_Style_Contract.md` — общий обязательный контракт Edit-экранов.**
   - Задаёт общий UI API из нейтральных `edit-*` и `label-*` stylename, единые роли sidebar/workspace, toolbar, карточек, полей, состояний и SCSS.
   - Для существующей формы требует preflight-аудит, карту `текущий элемент → общий stylename → нужный локальный класс`, минимальные presentation-only изменения, сохранение CUBA component IDs/data binding/business lifecycle и удаление legacy-стилей только после проверки зависимостей.
   - Для реализации задачи: сравнить каждый блок `specialisation-edit.xml` и локальный SCSS с контрактом; сохранить текущие поля, вкладки и действия, меняя только подтверждённые отклонения; учесть ограничения семи тем и контрактные проверки.

2. **`docs/ui/DictionaryEditForms_Spec.md` — прикладная спецификация серии справочных Edit-форм, включая `SpecialisationEdit`.**
   - Описывает назначение: специализации классифицируют направление работы кандидата и показывают связанных кандидатов.
   - Фиксирует двухпанельную композицию: sidebar 270px и рабочая область; для `SpecialisationEdit` — TabSheet с вкладками «Специализация» и «Кандидаты» и навигация по вкладкам; штатные data binding, loaders, контроллер и save lifecycle должны сохраняться.
   - В актуальной спецификации уже зафиксированы иллюстрация 176×176, живая подпись специализации, footer «Сохранить/Отмена», локальный namespace `specialisation-editor` и SCSS в семи темах.
   - Для реализации задачи: проверить, что текущие XML/Java/SCSS и тесты всё ещё совпадают с этими правилами; не переписывать заново уже реализованные элементы без конкретного расхождения.

3. **`docs/ui/ReestrBrowse_Design_Contract.md` — нормативный контракт Browse/Reestr-экранов.**
   - Задаёт общую структуру browse-реестра: корневой namespace и layout, workspace, toolbar/filter, таблицу, действия и состояния выбора, адаптивность, ограничение выборки и проверки загрузки данных.
   - Предусматривает исключения для чистого lookup-списка или экрана без Master-Detail, но исключение должно иметь явное обоснование в PR и комментарий в XML. Контракт не следует механически навязывать экрану, если он не подходит по бизнес-сценарию.
   - Для реализации задачи: определить, является ли `SpecialisationBrowse` стандартным управленческим реестром или простым lookup-списком; применить соответствующую композицию либо задокументировать обоснованное исключение.

### Что видно в текущих формах и коде

- `modules/web/src/com/company/hunttech/web/screens/specialisation/specialisation-edit.xml`: `SpecialisationEdit` уже использует полноэкранный modal, локальный `specialisation-editor`, общий `edit-screen-layout`, sidebar/workspace, `edit-toolbar`, `edit-card`, `edit-tabs`, поле `specRuName`, вкладку связанных кандидатов и `edit-footer-actions`.
- `SpecialisationEdit.java`: sidebar-кнопки переключают вкладки `tabSpecialisation` / `tabCandidate` и активное состояние; поведение presentation-only. Его следует сохранить, если не будет доказано отклонение от контракта.
- `specialisation-browse.xml`: сейчас диалог 800×600, стандартный `<filter>`, `groupTable` с единственной колонкой `specRuName`, стандартные create/edit/remove actions и кнопки. В XML нет контрактной композиции reestr/master-detail и собственных стилистических namespace-классов.
- `Specialisation.java`: справочник содержит `specRuName` и коллекцию связанных `JobCandidate`; имя уникально, удаление специализации с кандидатами запрещено (`DeletePolicy.DENY`). Browse/Edit должны сохранять эту семантику и ограничения.
- Документ `DictionaryEditForms_Spec.md` описывает Edit-экран, но не является отдельной спецификацией Browse-экрана; применимость Browse-контракта нужно определить по реальному сценарию lookup/manage.

### План действий по задаче

1. Сверить актуальные Browse/Edit XML, Java, SCSS во всех семи темах, существующие тесты и документацию с тремя нормативными документами выше.
2. Подготовить таблицу соответствия и список только доказанных отклонений отдельно для Edit и Browse.
3. Определить для Browse целевой режим: полноценный управленческий Browse по контракту либо документированное исключение для простого справочника/lookup. Сохранить фильтрацию, стандартные create/edit/remove, lookup-select/cancel и delete guard.
4. Устранить подтверждённые визуальные/структурные расхождения минимальным diff; сохранить component IDs, entity/data binding, список связанных кандидатов, права и lifecycle.
5. При необходимости добавить локальные scoped SCSS-классы, синхронизировать все семь тем; не использовать несопоставленные глобальные Vaadin-селекторы.
6. Обновить UI/entity-документацию и индекс, добавить контрактные тесты для Browse/Edit; выполнить screen-view integrity и требуемую SCSS-сборку.

## Классификация и контекст

Это IMPROVEMENT: запрос меняет и унифицирует существующие формы справочника; нового бизнес-сценария не описано. ## Предварительные критерии готовности

- Для Edit и Browse отдельно подготовлено сопоставление фактической формы с применимым контрактом и зафиксированы решения по исключениям.
- `SpecialisationEdit` следует общему Edit-контракту и прикладной спецификации; существующая композиция, связанные кандидаты, data binding и save lifecycle сохранены.
- `SpecialisationBrowse` соответствует контракту Browse/Reestr либо содержит явно обоснованное исключение в PR и XML.
- Работают create/edit/remove, lookup и выбор записи; запрет удаления используемой специализации сохранён.
- Не выполняются незаявленные изменения схемы/связей сущностей, включая BL-2026-039.
- Изменённая документация и контрактные проверки соответствуют финальному SHA; при правке SCSS синхронизированы все 7 тем.
