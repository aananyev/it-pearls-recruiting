## Изученная документация CUBA Platform

- [CUBA REST API 7.2 — официальная документация](https://doc.cuba-platform.com/restapi-7.2/) описывает CRUD, predefined JPQL, service methods, metadata, file operations и OAuth2. Документ требует настроить роли/группы доступа и поддерживать их в актуальном состоянии.
- [Security implications REST API](https://doc.cuba-platform.com/restapi-7.1/) требует отдельного REST security scope, отключения REST для неподходящих пользователей, deny-by-default и access group constraints. Документ отдельно предупреждает, что `EntityManager` не применяет ограничения групп доступа, поэтому middleware services должны использовать `DataManager` или эквивалентную проверку.
- [Roles and security scopes](https://doc.cuba-platform.com/manual-latest/roles.html) фиксирует раздельные наборы ролей для REST и Generic UI; REST add-on использует scope `REST`, а роли должны явно задавать разрешения.
- [Permissions](https://doc.cuba-platform.com/manual-latest/permissions.html) устанавливает deny-by-default: без соответствующего permission доступа нет; проверки operation permission должны выполняться через security subsystem.
- [Project-specific Swagger](https://doc.cuba-platform.com/manual-7.0/rest_swagger.html) описывает генерацию Swagger-документации для CRUD, queries и exposed services; итоговый HRM API должен иметь проверяемую versioned спецификацию.

## Обязательные решения плана

1. **Протокол и границы:** OAuth2 bearer tokens для CUBA REST; определить, нужен ли отдельный machine-to-machine grant/прокси для внешних приложений, допустимые scopes и versioned base path.
2. **Клиенты и секреты:** отдельный OAuth client на приложение/окружение, хранение secret вне репозитория, rotation/revocation, разные credentials для LOCAL/TEST/PROD.
3. **Роли CUBA:** отдельные REST-роли с `cuba.restApi.enabled`, deny-by-default, минимальными entity/attribute permissions и access-group constraints; не наследовать UI-роли без аудита.
4. **Публичный контракт:** узкие DTO, views и application services для Project/OpenPosition/Company/JobCandidate/CandidateCV/IteractionList; generic CRUD оставить закрытым или read-only.
5. **Проверки в middleware:** `DataManager`, Bean Validation, ownership/tenant rules, проверка справочников и связанных сущностей, отсутствие обхода security constraints через `EntityManager`.
6. **Надёжность:** idempotency keys, external IDs, correlation ID, атомарные транзакции, повторяемость запросов, таймауты, retry policy только на безопасных операциях и rate limit.
7. **Данные и приватность:** минимизация персональных данных, запрет секретов в логах, маскирование payload, безопасная передача файлов, лимиты размера/MIME и аудит доступа.
8. **Наблюдаемость:** журнал клиента/операции/статуса/latency/correlation ID без токенов, API keys и полного CV; метрики 4xx/5xx/429 и алерты.
9. **Документация:** OpenAPI/Swagger для каждой версии, auth flow, scopes, error schema, examples, backward compatibility и deprecation policy.
10. **Вывод в production:** security review, тесты негативных прав, секреты через environment/local properties, backup/rollback, smoke-тесты и отдельное разрешение на production deployment.

## Предварительные критерии готовности

- утверждён протокол, модель доверия и список внешних клиентов;
- для каждой операции есть owner, DTO, scope, роль и минимальный набор полей;
- доказано, что неавторизованный/неразрешённый клиент не читает и не изменяет данные;
- закрыты сценарии replay, дублирования, массовой отправки и утечки секретов;
- есть OpenAPI/Swagger, негативные тесты и runbook ротации ключей/отзыва клиента;
- план отдельно описывает LOCAL/TEST/PROD и не разрешает деплой одной только успешной сборкой.
