## Исходная мысль руководителя

> На будущее: надо внести в стандартный протокол доступа к нейросетям настройку прокси сервера для доступа. Сейчас на прод-сервере невозможен доступ к openrouter напрямую из-за геоблокирования.

## Проблема

Production не может напрямую обращаться к `https://openrouter.ai/api/v1/chat/completions` из-за геоблокирования. В текущем коде `OpenRouterProvider` задаёт прямой URL, а общий AI HTTP-слой не содержит утверждённой настройки proxy на уровне окружения/провайдера.

Нужен единый механизм маршрутизации исходящих AI-запросов через разрешённый proxy без копирования vendor-specific логики в каждом адаптере и без размещения proxy credentials в БД/исходном коде.

## Что проверено в коде и документации

- [OpenRouterProvider.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/core/src/com/company/hunttech/core/ai/OpenRouterProvider.java) использует прямой OpenRouter endpoint.
- [AbstractOpenAiCompatibleProvider.java](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/modules/core/src/com/company/hunttech/core/ai/AbstractOpenAiCompatibleProvider.java) централизует OpenAI-совместимые HTTP-запросы, авторизацию и таймауты; это естественная точка для общего proxy-aware HTTP-клиента.
- [AI_INTEGRATION.md](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/docs/integrations/ai/AI_INTEGRATION.md) описывает `AIProviderRegistry`, Control Plane и credential security, но не задаёт стандарт proxy для окружений.
- [USER_AI_SETTINGS_IMPLEMENTATION.md](/Users/alekseyananyev/StudioProjects/hunttech_recruiting/docs/integrations/ai/USER_AI_SETTINGS_IMPLEMENTATION.md) описывает тестирование доступности provider endpoint и предупреждает о сетевых/геоблокировочных причинах, но не даёт настраиваемого proxy-механизма.
- Проверку proxy нужно отделить от пользовательского API-ключа: пользовательская AI-конфигурация не должна хранить proxy credentials.

## Предварительный целевой протокол

- proxy настраивается централизованно по окружению (`LOCAL`, `TEST`, `PROD`) через защищённые properties/environment/secret storage;
- общий HTTP transport применяет proxy для разрешённых AI-провайдеров, а не только `OpenRouterProvider`;
- возможно выбирать `DIRECT`, `HTTP_PROXY` или `SOCKS` только если это требуется инфраструктурой и подтверждено безопасностью;
- proxy host/port, allowlist доменов, TLS/CA и credentials не попадают в UI, entity `UserAiConfiguration`, обычные логи и диагностические сообщения;
- health/test connection показывает различие `direct DNS/TLS`, `proxy connection`, `provider HTTP` без раскрытия токена;
- предусмотрены timeout, retry с ограничением, circuit breaker/controlled failure и fallback policy;
- production по умолчанию использует разрешённый маршрут, а обход proxy запрещён для provider-ов, которым нужен proxy.

Способ реализации (JVM proxy properties, отдельный HTTP client, корпоративный egress gateway или иной transport) должен быть выбран после инфраструктурной проверки, а не зафиксирован заранее в backlog.

## Требование к настройкам подключений к AI

В настройках AI-подключения должен быть виден и управляем применяемый сетевой маршрут:

- режим: `по умолчанию окружения`, `через proxy`, при необходимости `напрямую`;
- выбор разрешённого proxy-профиля или proxy-группы, а не ввод произвольного адреса обычным пользователем;
- безопасный тест подключения с указанием, прошёл ли запрос через proxy;
- отдельные права на просмотр/изменение proxy-настроек;
- proxy host, port, логин, пароль, токены и CA не должны отображаться в открытом виде и не должны храниться в `UserAiConfiguration` вместе с API-ключом;
- для корпоративных подключений настройка задаётся администратором, для персональных — только если это разрешено политикой;
- изменение маршрута должно иметь аудит и не менять provider/model/API key без отдельного действия.

Нужно решить, будет ли UI хранить только ссылку на защищённый proxy-профиль, а сами credentials — в окружении/secret storage. По умолчанию рекомендуемый вариант именно такой.

## Разделение пользовательских и административных настроек AI proxy

### Административные настройки

Раздел: `Администрирование → AI-подключения → Proxy-профили`. Администратор может создавать, изменять, отключать и проверять proxy-профили, задавать протокол, host/port, TLS/CA, таймауты и ссылку на секретное хранилище. Профиль назначается конкретному провайдеру, группе провайдеров или всем AI-подключениям. Администратор также задаёт доступные пользователям профили, маршрут по умолчанию и принудительные правила (например, обязательный корпоративный proxy для OpenRouter в PROD). Секреты не выводятся в UI и не сохраняются в `UserAiConfiguration`.

Статусы профиля: `Черновик`, `Активен`, `Отключён`, `Ошибка проверки`. Изменения профилей, правил, доступности и результаты тестов фиксируются в аудите.

### Пользовательские настройки

В форме пользовательского AI-подключения добавляется блок `Сетевой маршрут`. Пользователь может выбрать маршрут окружения по умолчанию или один из разрешённых proxy-профилей, увидеть назначение и состояние профиля, а также запустить безопасную проверку подключения. Пользователь не может вводить произвольный proxy-адрес, изменять реквизиты корпоративного proxy или обходить принудительное правило администратора. Выбор маршрута хранится отдельно для каждого AI-подключения.

### Приоритет маршрутизации

1. Принудительное правило окружения или администратора.
2. Административное назначение для провайдера или конкретного подключения.
3. Разрешённый выбор пользователя.
4. Маршрут по умолчанию провайдера.
5. Системный маршрут окружения.

Для production должна поддерживаться блокировка прямого доступа к OpenRouter при обязательном proxy.

### Роли и безопасное поведение

- **Администратор AI-подключений** — управляет профилями, правилами и диагностикой.
- **Пользователь AI-подключений** — выбирает только разрешённый маршрут принадлежащего ему подключения и запускает проверку.
- **Аудитор** — просматривает журнал изменений и проверок без секретов.

Проверка выполняется с теми же правилами маршрутизации, что и реальный AI-запрос. В аудите сохраняются профиль, пользователь, время, результат и технический код ошибки без реквизитов proxy. Отключённый профиль нельзя выбрать для нового подключения; существующее подключение должно возвращать безопасную диагностическую ошибку.

### Критерии приёмки уточнения

- администратор назначает активный proxy-профиль OpenRouter в PROD;
- пользователь видит только разрешённые профили и не видит секреты;
- принудительное правило перекрывает пользовательский выбор и прямое соединение;
- отключённый профиль нельзя сохранить для нового подключения;
- смена маршрута и проверка подключения попадают в аудит без конфиденциальных значений;
- UI объясняет, если маршрут задан принудительно или профиль недоступен.

## Предварительный план

1. Получить от DevOps параметры допустимого proxy, egress policy, TLS/CA, auth, allowlist `openrouter.ai` и правила ротации credentials.
2. Провести инвентаризацию всех AI HTTP-клиентов и провайдеров; определить, какие используют общий `AbstractOpenAiCompatibleProvider`, а какие собственный transport.
3. Спроектировать `AiNetworkConfiguration`/transport abstraction с fail-closed поведением, без хранения proxy secret в бизнес-сущностях.
4. Реализовать окруженческие настройки, маскирование, валидацию и безопасное логирование; добавить диагностику маршрута без токенов.
5. Проверить OpenRouter через proxy в LOCAL/TEST и затем отдельным разрешением в PROD; проверить прямой маршрут должен быть недоступен или явно запрещён политикой.
6. Добавить тесты HTTP transport: proxy on/off, proxy auth, timeout, TLS error, provider 401/429/5xx, no secret leakage, retry/circuit breaker.
7. Синхронизировать AI-документацию, deployment/runbook и инструкции ротации proxy credentials.

## Предварительные критерии готовности

- OpenRouter-запрос из production проходит через утверждённый proxy;
- провайдеры используют единый стандартный transport, где это предусмотрено архитектурой;
- proxy credentials не хранятся в БД, коде и логах;
- тест подключения различает сетевой/proxy/provider сбой;
- таймауты, retry и отказ proxy не приводят к зависанию фоновых AI-задач;
- прямой обход proxy соответствует утверждённой egress-политике;
- LOCAL/TEST не зависят от production-секретов;
- документация и runbook описывают включение, проверку, ротацию и rollback.
