# Отчет технического писателя: Исправление сохранения лимита токенов и добавление разового пополнения на текущий месяц в ExtUserEdit

**Дата:** 2026-09-14  
**Роли:** Аналитик, Java Backend-разработчик, Frontend-разработчик, Автоматизированный тестировщик (QA), Технический писатель  
**Статус:** Реализовано, протестировано, готово к поставке  

---

## 1. Назначение и контекст задачи

В карточке пользователя `ExtUserEdit` (вкладка «Персональный ИИ») администраторы настраивают квоты корпоративных моделей искусственного интеллекта.
Были выявлены и решены две проблемы:
1. **Несохранение постоянного месячного лимита:** при изменении администратором значения в поле «Выделено токенов» и сохранении карточки пользователя новое значение не сохранялось в базе данных.
2. **Отсутствие разового пополнения:** не было возможности выделить пользователю дополнительные токены на текущий календарный месяц (например, при исчерпании лимита в авральный период) без изменения постоянного месячного лимита и без риска, что эти токены перейдут на следующий месяц.

**Критическое требование:** Вся бизнес-логика управления лимитами, балансом, периодами и расчетом доступного объема токенов централизована исключительно в специализированном Java-сервисе `UserAiQuotaService`. Контроллеры экранов `ExtUserEditor` и `ExtUserEdit` не содержат бизнес-логики и прямых обращений к таблицам квот.

## 2. Специализированный сервис токенов (`UserAiQuotaService`)

### 2.1. Интерфейс и реализация
- **Интерфейс:** `com.company.hunttech.service.UserAiQuotaService` (модуль `global`).
- **Бин реализации:** `com.company.hunttech.service.UserAiQuotaServiceBean` (модуль `core`).
- **Связанный сервис выполнения LLM:** `com.company.hunttech.service.LlmChatServiceBean` (модуль `core`), вызывающий проверку квот в методе `reserveQuota`.

### 2.2. Архитектура хранения данных
1. **Постоянный персональный оверрайд лимита:**
   Сущность `LlmUserQuotaOverride` (таблица `HUNTTECH_LLM_USER_QUOTA_OVERRIDE`). Хранит персональный лимит пользователя (`quotaTokens`), который действует на постоянной основе, либо `-1` для безлимитного доступа. Если записи оверрайда нет, берется системная квота по умолчанию (`DEFAULT_MONTHLY_TOKEN_QUOTA = 1 000 000`).
2. **Учет расхода и бонусов по календарным месяцам:**
   Сущность `LlmChatQuotaPeriod` (таблица `HUNTTECH_LLM_CHAT_QUOTA_PERIOD`).
   - `user` — ссылка на пользователя (`sec$User`);
   - `periodStart` — дата начала календарного месяца (например, `2026-09-01`);
   - `periodEnd` — дата окончания календарного месяца (`2026-09-30 23:59:59`);
   - `quotaTokens` — зафиксированный базовый лимит на месяц;
   - `consumedTokens` — фактически израсходованные токены за месяц;
   - `extraTokens` (**новое поле**) — суммарный объем разовых дополнительных начислений, предоставленных администратором исключительно на этот календарный месяц.

### 2.3. Миграция базы данных
- **Liquibase:** `modules/core/db/changelog/260914-1-addExtraTokensToQuotaPeriod.xml` (зарегистрирован в `db.changelog-master.xml`).
- **PostgreSQL:** `modules/core/db/update/postgres/26/260914-1-addExtraTokensToQuotaPeriod.sql` (`ALTER TABLE HUNTTECH_LLM_CHAT_QUOTA_PERIOD ADD COLUMN EXTRA_TOKENS integer DEFAULT 0 NOT NULL;`).
- **HSQL:** `modules/core/db/update/hsql/26/260914-1-addExtraTokensToQuotaPeriod.sql`.
- Миграция успешно применена к локальной базе PostgreSQL.

## 3. Root Cause несохранения поля «Выделено токенов»

### 3.1. Анализ первопричины
В контроллере `ExtUserEditor.java` на этапе `postInit()` был зарегистрирован слушатель изменений datasource:
```java
userDs.addItemChangeListener(e -> {
    refreshProfileLabels();
    refreshAiConfigs();
    refreshAdminAiQuotaValues(); // <-- Перезагружает квоту из БД
});
```
При нажатии кнопки «ОК» («Сохранить») в `UserEditor` (родительском классе CUBA):
1. Метод `commitInternal` сначала фиксирует изменения `userDs` через `context.commit()`.
2. Обновление `userDs` мгновенно активирует событие `ItemChangeEvent`.
3. Срабатывает слушатель и вызывает `refreshAdminAiQuotaValues()`.
4. Метод `refreshAdminAiQuotaValues()` вычитывает из БД **старое** значение квоты, записывает его в текстовое поле `monthlyQuotaTokensField` и перезаписывает поле `initialQuotaTokens`.
5. Затем управление передается в `postCommit()`, где вызывался метод `saveAdminAiQuotaOverride()`.
6. Метод `saveAdminAiQuotaOverride()` сравнивает `initialQuotaTokens` и значение из поля — они оказываются равны, и обращение к `userAiQuotaService.setMonthlyQuota` просто не происходило.

### 3.2. Решение проблемы
1. Добавлены переменные состояния `pendingQuotaToSave` и флаг `pendingQuotaChanged`.
2. В цикле сохранения `preCommit()` введенное администратором значение валидируется и фиксируется в `pendingQuotaToSave`, а флаг `pendingQuotaChanged` выставляется в `true`.
3. В слушателе `userDs.addItemChangeListener` добавлен guard:
   ```java
   if (!pendingQuotaChanged) {
       refreshAdminAiQuotaValues();
   }
   ```
   Это полностью исключает перезапись введенного значения старыми данными из базы при коммите пользователя.
4. В `postCommit()` гарантированно вызывается `userAiQuotaService.setMonthlyQuota(...)` с переданным значением.
5. Логика синхронизирована как в `ExtUserEditor.java` (UserEditor legacy API), так и в `ExtUserEdit.java` (Screen API).

## 4. Бизнес-семантика разового пополнения («Добавить токенов»)

### 4.1. Добавленный метод сервиса
В интерфейс `UserAiQuotaService` и бин `UserAiQuotaServiceBean` добавлен метод:
```java
void addMonthlyBonusTokens(UUID userId, int amount, String reason);
```
- **Транзакционность:** Выполняется в транзакции `@Transactional`.
- **Атомарное увеличение:** Если запись `LlmChatQuotaPeriod` для текущего месяца уже существует, выполняется атомарное инкрементирование:
  `period.setExtraTokens(safeInt(period.getExtraTokens()) + amount);`
- **Аудит:** В историю начислений `LlmQuotaHistory` записывается аудит-событие с типом `EXTRA_BONUS_ADDED`, количеством начисленных токенов и обоснованием.

### 4.2. Централизованный расчет доступного объема токенов
Формула расчета остатка доступных токенов в `UserAiQuotaInfo`:
```text
effectiveLimit = allocatedTokens + extraTokens
availableTokens = Math.max(0, effectiveLimit - (consumedTokens + reservedTokens + pendingTokens))
```
- Для безлимитных пользователей (`allocatedTokens == -1`) `unlimited = true`, остаток не ограничен.
- Для лимитированных пользователей разовое пополнение увеличивает доступный объем, не меняя постоянный месячный лимит `allocatedTokens`.

### 4.3. Месячный период и сгорание бонусов без шедулера
- Период привязан к `periodStart = monthStart(today)` (1-е число календарного месяца).
- Начисление бонусов попадает строго в `LlmChatQuotaPeriod` текущего месяца.
- При наступлении нового месяца метод `getCurrentPeriod` автоматически создает/загружает запись нового месяца, в которой `extraTokens = 0`.
- Прошломесячные бонусы остаются в архивной записи за прошлый месяц для аудита и отчетности, но более не участвуют в расчетах нового месяца.
- Нет необходимости в тяжелых ночных планировщиках (sheduler/cron), что обеспечивает нулевую вероятность сбоев при переходе месяца.

### 4.4. Интеграция с реальным LLM-пайплайном
В `LlmChatServiceBean.java` в методе `reserveQuota` расчет допустимого лимита обновлен:
```java
int extraTokens = safeInt(period.getExtraTokens());
int totalAllowed = isUnlimited ? -1 : (safeInt(period.getQuotaTokens()) + extraTokens);
```
При исчерпании базового лимита начисление бонусных токенов мгновенно разблокирует выполнение последующих LLM-запросов пользователя.

## 5. Пользовательский интерфейс (UI)

1. **Компоновка:**
   Рядом с полем `Выделено токенов` (`monthlyQuotaTokensField`) расположена кнопка `Добавить токенов` (`addBonusTokensBtn`) со стилем `friendly` и иконкой `PLUS_CIRCLE`.
2. **Диалог ввода:**
   При нажатии на кнопку открывается стандартный модальный `InputDialog`:
   - Заголовок: `Добавить токенов на текущий месяц`
   - Подпись поля: `Количество токенов добавляется в этом месяце`
   - Валидация: строго целочисленное значение > 0 (`ValidationErrors` при пустом вводе, 0 или отрицательных числах).
   - Кнопки: `Добавить` (OK) и `Отмена` (CANCEL).
3. **Отображение бонуса в UI:**
   В поле `Остаток токенов` отображается текущий остаток, а при наличии активных бонусов добавляется пояснение: `(в т.ч. бонус на текущий месяц: +250 000)`.

## 6. Результаты тестирования

Создан комплексный тестовый класс `UserAiQuotaServiceContractTest`:
- **Test 1 — постоянный лимит:** изменение с 1 000 000 на 1 500 000, проверка сохранения и чтения.
- **Test 2 — пополнение:** базовый лимит 1 000 000, бонус 200 000, расход 0 -> доступно 1 200 000, постоянный лимит неизменен.
- **Test 3 — расход:** базовый лимит 1 000 000, бонус 200 000, расход 350 000 -> доступно 850 000.
- **Test 4 — несколько начислений:** начисление +200 000, затем +300 000 -> суммарно 500 000.
- **Test 5 — новый месяц:** в новом календарном месяце бонус предыдущего периода не участвует, эффективный лимит возвращается к базовому (1 000 000).
- **Test 6 — история:** сохранение записей прошлых периодов для аудита.
- **Test 7 — реальная проверка LLM:** проверка разблокировки запроса в `LlmChatServiceBean.reserveQuota` с учетом `extraTokens`.
- **Database and UI Contracts:** проверка Liquibase/SQL миграций, отсутствие дублирования логики в `ExtUserEditor` и `ExtUserEdit`.
