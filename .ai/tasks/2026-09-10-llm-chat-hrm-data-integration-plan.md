## 1. Цель и бизнес-контекст

### 1.1. Проблема
В текущей реализации плавающий LLM-чат (`LLM_CHAT`) является изолированным персональным ассистентом:
- Системный промпт функции `LLM_CHAT` явно содержит запрет: *«Не запрашивай и не обрабатывай данные кандидатов, CV и записи справочников HRM в этом MVP»*.
- В сервисе `LlmChatServiceBean` в контекст обращения к LLM передается исключительно текст запроса пользователя (`context.put("message", message)`).
- Пользователь не может получить ответы на практические рабочие вопросы: *«найди кандидатов с опытом Kotlin от 3 лет в Минске»*, *«объясни, какие последние взаимодействия были по кандидату Иванову»*, *«какие требования у вакансии Lead DevOps и кто по ней на этапе интервью»*.

### 1.2. Задача
Интегрировать LLM-чат с рабочими данными HRM в **строгом режиме чтения (READ-ONLY)**, позволяя ассистенту:
1. Автоматически или по явному запросу находить сущности:
   - **Открытые вакансии** (`OpenPosition`)
   - **Кандидаты** (`JobCandidate`, `Person`)
   - **Резюме и распарсенные компетенции** (`CandidateCV`, `SomeFilesCandidateCV`)
   - **История взаимодействий и комментариев** (`Iteraction`, `IteractionList`, `OpenPositionComment`)
   - **Подчиненные справочники** (`Skill`, `City`, `Company`, `Project`, `Grade` и др.)
2. Извлекать актуальные срезы данных с соблюдением политик безопасности (CUBA Security / Access Constraints).
3. Формировать для пользователя **сжатые, фактологические и структурированные доклады** на тему *«найди»*, *«объясни»*, *«сравни»*, *«подготовь сводку»*.
4. Предоставлять в ответах кликабельные ссылки/якоря для мгновенного перехода к сущностям в интерфейсе HRM.

## 2. Архитектурная концепция решения

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Пользовательский интерфейс                      │
│                (LlmChatScreen / Плавающий чат Vaadin)                  │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 1. Вопрос: "Найди Java в Москве..."
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                          LlmChatServiceBean                            │
│  - Управление сессией и историей                                       │
│  - Резервирование и сверка квот (LlmChatQuotaReservation)              │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 2. Проверка интента и поиск контекста
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                      HrmChatDataRetrieverService                       │
│                  (Строгий режим READ-ONLY, DataManager)                │
│  ├─ FTS Search (com.haulmont.fts.app.FtsService)                       │
│  ├─ Структурированные запросы (OpenPosition, JobCandidate, Iteraction) │
│  ├─ Проверка прав доступа текущего пользователя (Security)             │
│  └─ Сборка компактного HRM Context Snapshot (Markdown/JSON)            │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 3. message + hrmContextSnapshot
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                          AiExecutionService                            │
│  - Применение системного промпта LLM_CHAT (обновленного)               │
│  - Подмешивание персонализации "Обо мне" (UserAiContextService)        │
│  - Обращение к провайдеру LLM (Streaming / Non-Streaming)              │
│  - Аудит использования и учет токенов (AiCallLog)                      │
└────────────────────────────────────────────────────────────────────────┘
```

### Принципы архитектуры:
1. **Строгий READ-ONLY**: Чат не выполняет мутирующих операций (никаких INSERT, UPDATE, DELETE). Все операции выборки производятся через `DataManager` и `FtsService`.
2. **Data View Integrity**: Загрузка сущностей строго по задекларированным view (`*-llm-view`) во избежание `UnfetchedAttributeException` и lazy loading вне транзакции.
3. **Безопасность и контекст пользователя**: Выборка осуществляется строго в контексте текущей пользовательской сессии (`UserSessionSource.getUserSession()`), учитывая CUBA Row-Level Security и права на атрибуты.
4. **Контроль размера контекста (Token Budgeting)**: Выборка ограничивается релевантными записями (топ-5...топ-10 сущностей) и сжатым представлением (Summary), чтобы не перегружать токенами контекст модели и экономить пользовательскую квоту.
5. **Стабильный аудит и квотирование**: Все вызовы маршрутизируются через `AiExecutionService` с сохранением статистики в `AiCallLog` и списанием квот пользователя.

## 3. Детальный состав функционала

### 3.1. Модуль извлечения данных (`HrmChatDataRetrieverService`)
Создается новый бин сервисного слоя `com.company.hunttech.service.HrmChatDataRetrieverService`:
- **Анализ интента запроса**:
  - Распознавание запросов на поиск/объяснение данных системы (наличие ключевых слов рекрутинга, ФИО, названий компаний, вакансий, технологий, статусов).
- **Полнотекстовый поиск (FTS-слой)**:
  - Использование встроенного в HuntTech движка FTS (сконфигурированного в `modules/core/src/com/company/hunttech/fts.xml`) для быстрого поиска совпадений по ключевым словам в резюме, комментариях и описаниях вакансий.
- **Структурированный поиск (JPQL-слой)**:
  - Специализированные оптимизированные запросы с параметризацией для точного поиска:
    - По вакансиям: фильтры по наименованию, статусу (`active=true`), городу, грейду, стеку.
    - По кандидатам: фильтры по ФИО, желаемой должности, навыкам, рейтингу, городу.
    - По взаимодействиям: последние взаимодействия по кандидату/вакансии, комментарии, этапы.
- **Генерация компактного контекста (HRM Data Snapshot)**:
  - Преобразование найденных сущностей в лаконичный формат для передачи в LLM:
    ```markdown
    ### Срез данных HRM HuntTech (Read-Only):
    #### Вакансии (найдено 2):
    - [ID: a1b2c3d4] Senior Java Developer (Компания: FinTech Solutions, Город: Москва, З/П: от 350 000 руб., Статус: Открыта). Стек: Java 17, Spring Boot, Kafka, PostgreSQL.
    #### Кандидаты (найдено 3):
    - [ID: e5f6a7b8] Иванов Алексей Сергеевич (Java Backend, Опыт: 6 лет, Город: Москва). Ключевые навыки: Spring, Kafka, Docker.
      * Последнее взаимодействие (05.09.2026): Техническое интервью пройдено успешно, ожидается оффер.
    ```

### 3.2. Data View Integrity (Новые представления)
В `modules/global/src/com/company/hunttech/views.xml` объявляются легковесные view, содержащие только атрибуты, необходимые для формирования отчетов:
1. `open-position-llm-view`:
   - `vacansyName`, `status`, `openingDate`, `grade`, `city`, `project`, `company`, `departament`, `salaryMin`, `salaryMax`, `currency`, `shortDescription`.
2. `job-candidate-llm-view`:
   - `fullName`, `person`, `city`, `rate`, `currentCompany`, `jobCandidatePositionList`, `skills`, `salary`, `currency`, `lastContactDate`.
3. `iteraction-llm-view`:
   - `date`, `iteractionType`, `candidate`, `openPosition`, `comment`, `feedback`, `status`.
4. `candidate-cv-llm-view`:
   - `candidate`, `text`, `createTs`, `fileName`.

### 3.3. Обновление системного промпта `LLM_CHAT`
В системном промпте AI-функции `LLM_CHAT` (через Liquibase-миграцию):
1. Снимается запрет на обработку данных HRM.
2. Закрепляются новые системные инструкции:
   - *«Тебе предоставлен срез данных из рабочей базы HRM HuntTech (вакансии, кандидаты, резюме, взаимодействия).»*
   - *«При запросах вида "найди", "объясни", "сравни" опирайся строго на предоставленные факты из среза данных HRM. Если данных недостаточно, прямо сообщи об этом пользователю.»*
   - *«Формируй ответы структурированно, лаконично и профессионально (используй списки, краткие тезисы, сводные таблицы).»*
   - *«Указывай кликабельные маркеры сущностей вида `[Имя Кандидата](hrm://candidate/ID)` или `[Название Вакансии](hrm://vacancy/ID)` для удобной навигации.»*

### 3.4. Интерактивные ссылки и навигация в UI чата
- В `MarkdownRenderer.java` добавляется поддержка распознавания ссылок на сущности HRM:
  - `hrm://candidate/{id}` ➔ клик открывает экран редактирования/просмотра кандидата (`hunttech_JobCandidate.edit`).
  - `hrm://vacancy/{id}` ➔ клик открывает экран вакансии (`hunttech_OpenPosition.edit`).
  - `hrm://interaction/{id}` ➔ клик открывает карточку взаимодействия.
- Экран чата (`LlmChatScreen`) перехватывает клики по внутренним ссылкам и открывает соответствующие редакторы через стандартный `ScreenBuilders` CUBA Platform.

## 4. Сценарии использования (Use Cases)

### Сценарий 1: «Найди» (Поиск и подбор)
- **Запрос пользователя**: *«Найди среди кандидатов senior QA автоматизаторов на Python в Санкт-Петербурге или на удаленку»*
- **Действие системы**:
  1. `HrmChatDataRetrieverService` выполняет семантический и структурированный поиск в `JobCandidate` + `CandidateCV`.
  2. Извлекает топ-5 подходящих кандидатов со статусами и кратким стеком.
  3. LLM формирует сравнительную выжимку: список кандидатов, уровень соответствия требованиям, зарплатные ожидания и прямые ссылки на их профили.

### Сценарий 2: «Объясни / Расскажи историю» (Справка по воронке и кандидату)
- **Запрос пользователя**: *«Объясни, что сейчас происходит с кандидатом Петровым по вакансии Аналитик DWH? На каком он этапе и почему задержка?»*
- **Действие системы**:
  1. Сервис находит кандидата Петрова и связанные взаимодействия `Iteraction` по указанной позиции.
  2. Формирует хронологию событий с датами, комментариями интервьюеров и текущим статусом.
  3. LLM генерирует сжатый отчет: *«Кандидат прошел скрининг 28.08, техническое интервью 02.09 (оценка 4/5, сильный SQL). Задержка вызвана согласованием оффера с заказчиком (комментарий от 05.09: ожидается ответ финдиректора)»*.

### Сценарий 3: «Сводка / Аналитика» (Executive Summary)
- **Запрос пользователя**: *«Сделай краткую сводку по открытым вакансиям в отделе Мобильной разработки: какие позиции горящие и сколько кандидатов в работе?»*
- **Действие системы**:
  1. Сервис загружает открытые позиции отдела `Mobile Development` и агрегирует количество прикрепленных кандидатов по этапам воронки.
  2. LLM выдает компактную таблицу: вакансия | грейд | в воронке | на финале | риски.

## 5. План поэтапной реализации

### Этап 1. Документация, View и Контракты (Аналитик + Backend)
1. Создание сервисного интерфейса `HrmChatDataRetrieverService` в `modules/global`.
2. Описание view для сущностей `OpenPosition`, `JobCandidate`, `Iteraction`, `CandidateCV` в `modules/global/src/com/company/hunttech/views.xml`.
3. Разработка DTO для срезов контекста данных: `HrmDataContextSnapshot`, `HrmEntitySummary`.

### Этап 2. Реализация ядра извлечения данных (Java Backend-разработчик)
1. Реализация `HrmChatDataRetrieverServiceBean` в `modules/core`:
   - Логика распознавания интентов и выделения сущностей.
   - Запросы к `DataManager` и FTS с контролем прав доступа `Security`.
   - Ограничение объема выборки (Token Budgeting, лимит до 2000 токенов).
2. Интеграция в `LlmChatServiceBean`:
   - Обогащение контекста вызова `aiExecutionService.executeText` и `executeTextStreaming` найденным срезом данных `hrmContextSnapshot`.

### Этап 3. Системные данные и промпты (Backend-разработчик)
1. Создание Liquibase-миграции обновления `system_prompt` для AI-функции `LLM_CHAT`.
2. Тестирование списания квот (`LlmChatQuotaPeriod` / `AiCallLog`) с учетом увеличенного контекста данных.

### Этап 4. UI и навигация в чате (UI/UX-дизайнер + Frontend-разработчик)
1. Обновление `MarkdownRenderer`: поддержка кастомных ссылок `hrm://...` со стилизацией под тег/ссылку системы.
2. Обработка кликов в `LlmChatScreen`: бесшовное открытие экранов CUBA (`ScreenBuilders.editor(...)`).

### Этап 5. Автотестирование и валидация (Тестировщик QA + Alibaba OCR)
1. Написание модульных и интеграционных тестов:
   - `HrmChatDataRetrieverServiceTest`: корректность извлечения сущностей, отсутствие утечек чужих данных.
   - `DataViewIntegrityTest`: отсутствие `UnfetchedAttributeException`.
   - `LlmChatDataIntegrationTest`: проверка формирования контекста и генерации ответа.
2. Проверка кода через Alibaba OCR (`ocr review --audience agent`).

## 6. Управление рисками и ограничения

| Риск | Вероятность | Влияние | Мера предотвращения |
| :--- | :---: | :---: | :--- |
| **Превышение контекстного окна модели** | Средняя | Высокое | Жесткий лимит сущностей (Top-5...Top-10), агрегация текста резюме до ключевых блоков. |
| **Утечка персональных данных (ПДн)** | Низкая | Критическое | Извлечение строго через `DataManager` с проверкой прав `Security` текущего пользователя; системные пароли/секреты исключены из view. |
| **UnfetchedAttributeException при обходе связей** | Средняя | Высокое | Все связанные справочники (`City`, `Grade`, `Project`) явно декларируются в `*-llm-view`. |
| **Повышенный расход квоты токенов** | Средняя | Среднее | Оптимизированный компактный формат Markdown без избыточного JSON/XML оверхеда. |
