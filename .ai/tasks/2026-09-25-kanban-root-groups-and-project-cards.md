# Аналитический отчет и спецификация: Разделение карточек Канбана по проектам и формирование колонок по главным группам взаимодействий (Iteraction)

- **Дата**: 2026-09-25
- **Роли**: Руководитель проектов (Project Manager), Аналитик (Analyst), Главный разработчик (Tech Lead)
- **Компоненты**: `RecruiterCandidateKanbanWidget.java`, `views.xml`, `recruiter-candidate-kanban-widget.xml`, `RecruiterDashboardsContractTest.java`

---

## 1. Контекст и бизнес-цель

В HRM HuntTech виджет «Кандидаты в работе (Kanban)» отображает воронку подбора кандидатов.
Пользователем поставлены две фундаментальные задачи:
1. **Разделение карточек по проектам (вакансиям)**:
   - Ранее доска дедуплицировала кандидата полностью (`UUID candidateId = candidate.getId()`), оставляя лишь одно взаимодействие на одного человека и скрывая его участие в других проектах.
   - Требование: Кандидат может одновременно проходить отбор по нескольким проектам (вакансиям). Карточка на Канбан-доске формируется для каждого проекта/вакансии кандидата отдельно, с отображением последнего взаимодействия по этому проекту.
   - Бизнес-пример: Кандидат Новиков Всеволод за последний месяц проходит по 2-м проектам:
     - Проект ДКС «Проекты Дениса Попенова» /Штат Hunttech/ — последнее взаимодействие «Назначено собеседование с рекрутером Hunttech» (карточка 1 в соответствующей колонке этапа).
     - Проект АГИМА «Банк. Проект Лясан Маннанновой /Штат Hunttech/» — последнее взаимодействие «Прошел техническое собеседование на стороне заказчика» (карточка 2 в колонке «На стороне заказчика»).

2. **Формирование колонок Канбана по главным группам справочника взаимодействий (`Iteraction`)**:
   - В таблице `HUNTTECH_ITERACTION` (`hunttech_Iteraction`) взаимодействия имеют древовидную двухуровневую структуру:
     - Корневые записи (`iteractionTree IS NULL`, `number_ IS NOT NULL`) определяют главные группы процесса найма.
     - Дочерние записи (`iteractionTree` ссылается на корень) являются конкретными действиями (навыками взаимодействия).
   - Главные корневые группы этапов подбора:
     - `001 Ресерчинг`
     - `002 Хантинг`
     - `003 На стороне заказчика`
     - `008 УСПЕХ` (Оффер / Финал)
     - `007 ОТКАЗ` / `010 Закрытие кейса`
   - Колонки на Канбан-доске должны формироваться в соответствии с главными группами справочника `Iteraction`. Каждое взаимодействие кандидата относится к своей главной корневой группе (через `iteraction.getIteractionTree()` или сам корень), и карточка помещается в колонку этой группы.

## 2. Архитектурное решение

### 2.1. Расширение Data View (`views.xml`)
В соответствии с правилом `Data View Integrity` (`.cursor/rules/data-view-integrity.mdc`) view `recruiter-dashboard-iteraction-list-view` дополняется свойствами:
```xml
<property name="iteractionType" view="_minimal">
    <property name="iterationName"/>
    <property name="number"/>
    <property name="iteractionTree" view="_minimal">
        <property name="iterationName"/>
        <property name="number"/>
    </property>
    ...
</property>
```
Это исключает N+1 запросы и `IllegalStateException (Unfetched Attribute Access)`.

### 2.2. Алгоритм группировки и уникальности карточек
- Ключ уникальности карточки: `candidateId + "_" + (vacancyId != null ? vacancyId : "no_vacancy")`.
- Для каждой пары `(candidate, vacancy)` отбирается самое последнее взаимодействие (по максимальному `numberIteraction` / `dateIteraction`).
- Для полученного последнего взаимодействия определяется его главная группа (корневой `Iteraction` с `iteractionTree == null`).
- Карточка помещается в колонку соответствующей главной группы.

### 2.3. Набор и порядок колонок Канбана
Колонки Канбана формируются по главным этапам подбора:
1. `Ресерчинг` (код 001)
2. `Хантинг` (код 002)
3. `На стороне заказчика` (код 003)
4. `УСПЕХ` (код 008, Оффер / Выход)
5. `ОТКАЗ / Закрытие` (коды 007, 010)

Взаимодействия со знаком кадрового резерва (`signPersonalReserve`) не загромождают воронку активного подбора (для них предназначен специализированный экран `RecruiterTalentReserveWidget`).

### 2.4. Сохранение и адаптация KPI-панели
Верхняя панель метрик (`kpiBar`) пересчитывает показатели по актуальным активным кейсам (с учетом проектов) и ключевым этапам воронки найма.

## 3. Критерии приемки (DoD)
1. Кандидат с несколькими проектами отображается в виде нескольких независимых карточек (по одной на каждый проект).
2. Название колонок соответствует наименованиям главных групп взаимодействий.
3. Карточки распределяются в колонки строго по главной группе своего последнего взаимодействия по данному проекту.
4. Отсутствуют ошибки `Unfetched attribute` благодаря корректному `views.xml`.
5. Контрактные тесты `RecruiterDashboardsContractTest` успешно проходят.
6. Выполнен ocr-контроль качества кода.
