# Отчёт о недоступности AI-подбора вакансий и fallback OpenRouter → DeepSeek

## Назначение и бизнес-смысл (What & Why)

Отчёт фиксирует причину, по которой AI-операции HRM HuntTech не переходят с недоступного OpenRouter на доступный DeepSeek, и определяет варианты восстановления. Диагностика выполнена в режиме только чтения: production-конфигурация, журналы вызовов и данные не изменялись.

## UI Context & Navigation

- экран: диалог «Подобрать вакансию», открываемый из карточки кандидата;
- основной AI-анализ соответствия: `CANDIDATE_VACANCY_MATCH_ANALYZE`;
- предварительное обновление навыков: `SKILLS_EXTRACT` при интерактивном вызове и `SKILLS_EXTRACT_BACKGROUND` в фоновом воркере;
- дата диагностики: 2026-09-21;
- фактический production-релиз: `0.684-SNAPSHOT`, JAR `app-core-0.684-SNAPSHOT.jar` от 2026-09-21.

## Behavior Summary

| Действие | Условие | Фактический результат |
|---|---|---|
| Вызов OpenRouter | Баланс исчерпан | `HTTP 402 Insufficient credits`, выполняются три попытки |
| Переход к следующей корпоративной конфигурации | Следующий OpenRouter содержит нерасшифровываемый credential | Исключение выходит из цикла fallback, DeepSeek не вызывается |
| Фоновое обновление навыков | `hunttech.skillsEnrichment.freeOnly=true` | Платный DeepSeek исключается из списка кандидатов по политике |
| Интерактивный AI-подбор | DeepSeek активен и исправен | DeepSeek должен входить в список, но его может заблокировать ошибка credential предыдущего кандидата |

## Подтверждённые факты production

1. OpenRouter Nemotron недоступен из-за исчерпанного баланса. В `hunttech_ai_call_log` повторяется `HTTP 402 Insufficient credits`.
2. Журнал приложения подтверждает исчерпание трёх попыток и сообщение о переходе к следующей сети.
3. Следующая активная OpenRouter-конфигурация завершается `DevelopmentException: Не удалось расшифровать корпоративный AI credential`. По порядку активных кандидатов это соответствует Inkling; прямой идентификатор конфигурации в тексте исключения отсутствует, поэтому связь является выводом из порядка маршрутизации.
4. Корпоративный DeepSeek активен: модель `deepseek-v4-flash`, ключ присутствует, последний тест подключения имеет статус `SUCCESS`.
5. `CANDIDATE_VACANCY_MATCH_ANALYZE` активна, имеет политику `USER_OVERRIDE_ALLOWED / FALLBACK_TO_ADMIN` и привязана к OpenRouter Nemotron.
6. `SKILLS_EXTRACT_BACKGROUND` имеет политику `ADMIN_ONLY / NO_FALLBACK`, привязана к OpenRouter Nemotron; системный параметр `hunttech.skillsEnrichment.freeOnly=true`.
7. DeepSeek отмечен как платная модель (`is_free_model=false`), поэтому фоновый режим `freeOnly` корректно исключает его.
8. Персональные подключения пользователя `alan` для OpenRouter и DeepSeek неактивны и не участвуют в маршрутизации.
9. В production-журнале на момент проверки нет вызовов `CANDIDATE_VACANCY_MATCH_ANALYZE`: новая экранная цепочка PR ещё не развёрнута и не подтверждена production-вызовом.

## Состояние репозитория после диагностики

После фиксации production-фактов в `master` появилась миграция `260921-1-routeCandidateVacancyMatchToDeepSeek.sql`. Она напрямую переводит `CANDIDATE_VACANCY_MATCH_ANALYZE` с OpenRouter Nemotron на единственную активную конфигурацию DeepSeek и имеет отдельный rollback и контрактный тест.

Это оперативное исправление соответствует варианту 3 ниже и снижает риск интерактивного подбора после применения миграции. Оно не устраняет общий дефект маршрутизатора: нерасшифровываемый credential по-прежнему может оборвать fallback других AI-функций. Применение этой миграции на production в рамках данной диагностики не выполнялось и не подтверждалось.

## Корневая причина

В актуальном production уже присутствует централизованный перебор корпоративных AI-подключений. Ошибка находится в границе обработки одного кандидата.

В `AiExecutionServiceBean` расшифровка ключа выполняется до внутреннего `try/catch`, который должен зарегистрировать отказ текущей конфигурации и продолжить цикл:

- текстовые запросы: `executeWithAdminCandidatesText`, расшифровка около строки 655;
- потоковые запросы: `executeWithAdminCandidatesStreaming`, расшифровка около строки 788;
- изображения: `executeWithAdminCandidatesImage`, расшифровка около строки 912.

Когда резервная конфигурация содержит credential, который нельзя расшифровать текущим master key, исключение не считается отказом отдельного провайдера. Оно покидает весь метод и обрывает цикл до DeepSeek.

```text
OpenRouter Nemotron
        ↓ HTTP 402, три попытки
следующий активный OpenRouter
        ↓ ошибка расшифровки credential вне per-candidate try/catch
весь AI-вызов завершается ошибкой
        ↓
DeepSeek не вызывается
```

Для `SKILLS_EXTRACT_BACKGROUND` действует дополнительное независимое ограничение: при `freeOnly=true` платный DeepSeek не может быть резервом по действующей политике, даже после исправления обработки credential.

## Почему доступный DeepSeek не используется

Для интерактивного `CANDIDATE_VACANCY_MATCH_ANALYZE` DeepSeek должен входить в общий список активных корпоративных кандидатов. До него не доходит выполнение из-за необработанной ошибки расшифровки предыдущей OpenRouter-конфигурации.

Для фонового `SKILLS_EXTRACT_BACKGROUND` DeepSeek отсекается раньше маршрутизации, потому что функция разрешает только бесплатные модели, а DeepSeek в базе помечен платным.

Это две разные причины, поэтому одной смены приоритета недостаточно для устойчивого исправления.

## Варианты исправления

### Вариант 1. Изолировать ошибки каждой AI-конфигурации — рекомендуемый

Перенести расшифровку credential и подготовку параметров провайдера внутрь обработки отдельного кандидата. Ошибку расшифровки фиксировать как отказ конкретной конфигурации, безопасно пропускать её и продолжать перебор.

Изменение требуется одинаково для text, streaming и image путей. Регрессионный сценарий: OpenRouter возвращает `402` → следующий OpenRouter имеет невалидный encrypted credential → DeepSeek успешно отвечает.

Преимущества:

- один повреждённый credential не блокирует остальные провайдеры;
- сохраняется общий порядок и политика маршрутизации;
- дефект устраняется для всех AI-функций, а не только для формы подбора.

### Вариант 2. Исправить или отключить неисправную OpenRouter-конфигурацию

Проверить предполагаемую OpenRouter Inkling конфигурацию и, после подтверждения по ID, повторно сохранить её ключ с текущим master key либо отключить конфигурацию до исправления. Это оперативно освобождает путь к DeepSeek, но не устраняет дефект маршрутизатора: следующая нерасшифровываемая запись снова оборвёт fallback.

### Вариант 3. Временно назначить DeepSeek основной моделью интерактивных функций

Привязать `CANDIDATE_VACANCY_MATCH_ANALYZE` и `SKILLS_EXTRACT` к рабочему корпоративному DeepSeek. Это сокращает время восстановления интерактивного сценария, но не заменяет исправление общего маршрутизатора.

### Вариант 4. Изменить политику фонового анализа навыков

Если бизнес допускает платный DeepSeek в фоне, установить `hunttech.skillsEnrichment.freeOnly=false` и проверить бюджетные ограничения. Не следует помечать платную модель бесплатной ради обхода фильтра.

Если фон должен оставаться бесплатным, необходимо восстановить рабочую бесплатную модель OpenRouter или добавить другой бесплатный провайдер.

### Вариант 5. Сократить обработку постоянных ошибок провайдера

Для `401/402/403` выполнять немедленное переключение без трёх одинаковых повторов. Для `429`, timeout и `5xx` оставить ограниченный retry. Дополнительно можно ввести временное исключение неисправной конфигурации после серии отказов.

### Вариант 6. Пополнить баланс OpenRouter

Устраняет текущий `HTTP 402`, но не исправляет блокировку цепочки ошибкой credential и не даёт устойчивого fallback.

## Рекомендованный порядок

1. Исправить общий маршрутизатор по варианту 1 и покрыть text, streaming и image тестами.
2. Повторно сохранить либо временно отключить неисправную OpenRouter Inkling конфигурацию.
3. Отдельно принять решение по стоимости фонового анализа: разрешить платный DeepSeek или сохранить `freeOnly` и восстановить бесплатного провайдера.
4. Через Hermes проверить точный HEAD: OpenRouter `402` → ошибка credential резервного OpenRouter → DeepSeek `SUCCESS`.
5. После развёртывания выполнить smoke диалога «Подобрать вакансию» и проверить выход UI из состояния ожидания.

Production-конфигурация в рамках диагностики не менялась. Любая перепривязка функции, изменение `freeOnly` или credential требует отдельной прямой команды на изменение production.

## Критерии приёмки исправления

- итоговый успешный вызов имеет `provider_code=deepseek`;
- `model_switch_count` отражает фактические переключения;
- ошибка расшифровки одной конфигурации присутствует в журнале, но не завершает общий вызов;
- `CANDIDATE_VACANCY_MATCH_ANALYZE` возвращает валидный JSON-контракт подбора;
- `SKILLS_EXTRACT` фиксирует навыки без дублей;
- поведение `SKILLS_EXTRACT_BACKGROUND` соответствует явно выбранной политике стоимости;
- форма показывает текущий этап, процент, оценку оставшегося времени и конечный результат либо понятную ошибку с действием «Повторить».
