# Решение по lookup usage у LLM-провайдеров

Дата решения: 2026-09-05

## Решение

В текущий релиз не добавлять автоматический запрос usage по одному `providerRequestId`. Реализовать его можно только после отдельного подтверждения контракта конкретного провайдера: endpoint, права ключа, регион, срок доступности данных и семантика идентификатора должны быть зафиксированы для каждого адаптера.

Причина: наличие идентификатора ответа не означает наличие публичного API для повторного получения usage. В официальной документации OpenAI Usage API описан как агрегированный организационный отчёт по периоду и фильтрам, а `X-Request-Id`/`X-Client-Request-Id` описаны для диагностики и обращения в поддержку, но не как универсальный lookup endpoint: [Usage API](https://platform.openai.com/docs/api-reference/usage/audio_transcriptions_object), [Debugging requests](https://platform.openai.com/docs/api-reference/debugging-requests?lang=curl). Поэтому предположительный повторный вызов провайдера создавал бы риск двойного списания и нарушения идемпотентности.

## Текущий fail-closed контракт

- подтверждённый callback с фактическим usage закрывает reservation автоматически;
- один `providerRequestId` без usage оставляет reservation в `UNKNOWN_PENDING`;
- повторный вызов провайдера для сверки не выполняется;
- администратор закрывает запись через `reconcileUnknown()` с audit actor и причиной;
- пользователь видит понятное состояние неопределённого списания, а не получает молча неверный остаток квоты.

## Условия для следующей реализации

Перед добавлением capability-based lookup для провайдера нужно получить и проверить:

- официальный endpoint и пример ответа с prompt/completion/total tokens;
- требуемую область доступа ключа и ограничения региона;
- гарантии идемпотентности и срок хранения результата;
- rate limit и поведение при `404`, `429`, `5xx`;
- соответствие `providerRequestId` запросу HRM и отсутствие необходимости повторно отправлять prompt или персональный контекст.

После подтверждения capability добавляется только в соответствующий адаптер. Общий сервис сохраняет `UNKNOWN_PENDING` для адаптеров без capability; схема данных и ручная сверка остаются обратимо совместимыми.

## Миграции

Изменений сущностей, Liquibase changeSet и seed-данных для этого решения нет.
