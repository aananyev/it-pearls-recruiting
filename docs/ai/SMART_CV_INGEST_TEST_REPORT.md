## 1. Паспорт объекта тестирования и цели

Функция «Умное заведение карточки кандидата» предназначена для автоматического извлечения структурированных данных о кандидате из файлов резюме, веб-страниц или сырого текста с помощью LLM (AI Control Plane) и создания в HRM связанных сущностей:
- `JobCandidate` (карточка кандидата, контакты, город, текущее место работы);
- `CandidateCV` (версия резюме, исходный файл в FileStorage, текст резюме);
- `JobHistory` (хронологическая цепочка мест работы, даты, обязанности, достижения);
- `CandidateSkill` (навыки кандидата, привязка к справочнику `SkillTree`);
- `Company` (компании-работодатели с автосозданием и очисткой названий);
- `IteractionList` (первичное взаимодействие рекрутера с фиксацией зарплатных ожиданий).

### Исследованные точки входа в систему:
1. **Экран «Реестр кандидатов»** (`JobCandidateReestr.java` / `job-candidate-browse.xml`) — кнопка тулбара `smartUploadBtn` («Умная загрузка»).
2. **Экран «Реестр резюме кандидатов»** (`CandidateCVReestrBrowse.java` / `candidate-cv-reestr-browse.xml`) — кнопка тулбара `smartUploadBtn` («Умная загрузка»).
3. **Интерактивный мастер** `SmartCvUploadScreen` (`smart-cv-upload-screen.xml`):
   - Вкладка 1: «Загрузить файл» (Drag-and-Drop, FileUploadField).
   - Вкладка 2: «Вставить текст» (RichTextArea, кнопка «Анализировать текст»).
   - Вкладка 3: «Загрузить по ссылке» (TextField для URL, извлечение через Jsoup).
4. **Бэкенд-сервис** `SmartCvIngestServiceBean` и AI-функция `CV_SMART_PARSE_JSON` (`AiExecutionService`).

## 4. Реестр найденных дефектов

### Дефект 1 (Критический): Баг регулярного выражения в очистке наименований компаний (`cleanCompanyName`)
- **Компонент**: `SmartCvIngestServiceBean.java` (строка 815).
- **Симптом**: При импорте компании с организационно-правовой формой на кириллице (например, `ООО "Яндекс"`, `ПАО «Сбербанк»`, `ЗАО "Крок"`), правовая форма **не удаляется**, и компания сохраняется как `ООО Яндекс` вместо `Яндекс`.
- **Причина**: В регулярном выражении `raw.replaceAll("(?i)(ооо|зао|пао|ао|ип|нко|ltd|llc|inc|gmbh|corp)\\b", "")` граница слова `\b` в стандартном движке Java regex рассчитывается только по ASCII-символам `[a-zA-Z0-9_]`. Кириллические символы не считаются словесными без флага `(?U)` (Unicode character class).
- **Влияние на систему**:
  1. В справочнике `Company` плодятся дубликаты («ООО Яндекс», «Яндекс», «ООО "Яндекс"»).
  2. Механизм дедупликации компаний `resolveOrCreateCompany` не может найти существующую компанию по чистому имени.
- **Способ устранения**:
  ```java
  // Было:
  return raw.replaceAll("(?i)(ооо|зао|пао|ао|ип|нко|ltd|llc|inc|gmbh|corp)\\b", "")
  // Должно быть:
  return raw.replaceAll("(?iU)\\b(ооо|зао|пао|ао|ип|нко|ltd|llc|inc|gmbh|corp)\\b", "")
          .replaceAll("[\"«»'„“]", "")
          .trim();
  ```

### Дефект 2 (Существенный): Сбой дедупликации кандидатов по номеру телефона (`findDuplicate`)
- **Компонент**: `SmartCvIngestServiceBean.java` (строки 249–260).
- **Симптом**: Если кандидат уже есть в базе с телефоном `+7 (999) 111-22-33`, повторная загрузка резюме с телефоном `8-999-111-2233` или `+79991112233` **не распознает дубликат** и предлагает создать новую запись.
- **Причина**: Сервис берет последние 10 цифр (`9991112233`) и выполняет запрос:
  ```jpql
  select e from hunttech_JobCandidate e where e.phone like :digits or e.mobilePhone like :digits
  ```
  где `:digits = "%9991112233%"`. В базе данных телефон сохранен со скобками, пробелами и дефисами (`+7 (999) 111-22-33`), поэтому подстрока из 10 слитных цифр `9991112233` в нем отсутствует!
- **Влияние на систему**: Дубликаты кандидатов не отлавливаются по основному идентификатору рекрутинга — номеру мобильного телефона, если в базе хранятся маскированные значения.
- **Способ устранения**:
  1. Либо выполнять очистку символов на уровне SQL/JPQL:
     `where regexp_replace(e.phone, '\D', '', 'g') like :digits` (для PostgreSQL).
  2. Либо в сущности `JobCandidate` сохранять нормализованный телефон без разделителей в специальное поле `phoneDigits`, по которому строить индекс и производить мгновенный точный поиск.

### Дефект 3 (Средний): Потеря фокуса таблицы после успешного сохранения (`setSelected`)
- **Компонент**: `JobCandidateReestr.java` (строка 929) и `CandidateCVReestrBrowse.java` (строка 287).
- **Симптом**: После создания кандидата через «Умную загрузку» таблица перезагружается, но созданная строка не выделяется фокусом, либо выделение сбрасывается.
- **Причина**: Контроллер вызывает `candidatesTable.setSelected(screen.getCreatedCandidate())`. Но перед этим вызывается `setCandidateScopeFilter` / `jobCandidatesDl.load()`, который заново создает экземпляры сущностей в `candidatesDc`. Передаваемый объект `createdCandidate` принадлежит предыдущему persistence/data-context и не идентичен инстансу внутри контейнера.
- **Способ устранения**:
  Искать сущность по идентификатору в контейнере:
  ```java
  JobCandidate inContainer = candidatesDc.getItemOrNull(screen.getCreatedCandidate().getId());
  if (inContainer != null) {
      candidatesTable.setSelected(inContainer);
  }
  ```

### Дефект 4 (Низкий): Потеря несловарной должности в карточке кандидата
- **Компонент**: `SmartCvIngestServiceBean.java` (строки 331–335, 723–739).
- **Симптом**: Если желаемая должность из резюме (например, «Golang Tech Lead») отсутствует в справочнике `Position`, поле `candidate.personPosition` остается `null`. На экране реестра кандидат отображается без должности (пустая колонка), хотя в UI мастера должность отображалась.
- **Причина**: Сущность `JobCandidate` имеет только связь `Position personPosition` (справочник), но не имеет строкового поля `rawPosition`. При этом в `JobHistory` поле `rawPositionName` сохраняется успешно.
- **Рекомендация**: При отсутствии должности в справочнике добавлять строковую должность в саммари/комментарий кандидата, либо создать справочную запись с флагом «Требует модерации».

## 5. Экспертный аудит системного промпта `CV_SMART_PARSE_JSON` (Субагент «Промпт-инженер»)

Субагент «Промпт-инженер» провел детальный анализ текущего системного промпта из миграции `260821-4-updateSmartCvParseAiFunction.xml`.

### 5.1. Анализ текущей версии промпта
```text
Ты — интеллектуальный модуль распознавания резюме HRM HuntTech. Твоя задача — внимательно изучить текст резюме и извлечь все структурированные данные о кандидате, его образовании и полной истории мест работы. Верни строго один JSON-объект следующей структуры: {"lastName": "Фамилия", "firstName": "Имя", ...}
```

### 5.2. Выявленные слабые места и риски:
1. **Засорение полей маркерами отсутствия данных**: Модели часто возвращают `"salary": "Не указано"`, `"middleName": "Нет"`, `"telegram": "N/A"`. При сохранении в базу кандидат получает реальное отчество `"Нет"` или зарплату `"Не указано"`.
2. **Проблема неатомарных навыков**: Без строгого правила модель возвращает составные строки: `["Java, Spring, Hibernate", "Управление командой и Agile"]`. В HRM сопоставление со `SkillTree` идет по точному имени, поэтому такие навыки не распознаются справочником.
3. **Галлюцинации дат рождения**: При наличии в резюме только возраста («32 года») модели часто генерируют случайную дату, например текущий день минус 32 года (`1994-09-13`), что искажает реальный день рождения.
4. **Хронологическая инверсия опыта**: В резюме с HeadHunter опыт идет от последнего места к первому. Промпт требует сортировку от ранних к поздним, но без явных примеров модели часто путают хронологию.
5. **Мусор в названиях должностей**: Модели часто включают в должность грейды и локации («Ведущий инженер-программист (удаленно, РФ)»).

## 7. Фактически реализованные улучшения и устранение дефектов

По результатам тестирования и прямому указанию пользователя рабочей группой субагентов выполнены следующие доработки:

1. **Устранение Дефекта 1 (Regex в `cleanCompanyName`)**:
   В `SmartCvIngestServiceBean.java` регулярное выражение обновлено до `(?iU)\b(ооо|зао|пао|ао|ип|нко|ltd|llc|inc|gmbh|corp)\b`. Теперь правовые формы на кириллице («ООО», «ПАО», «ЗАО») гарантированно отсекаются, предотвращая засорение справочника компаний.
2. **Устранение Дефекта 2 (Дедупликация по телефону с масками и разделителями)**:
   В `SmartCvIngestServiceBean.findDuplicate` реализован двухуровневый алгоритм: прямой поиск по слитным цифрам и поиск по маскированным шаблонам `%p1%p2%p3%p4%` с последующей валидацией последних 10 цифр на уровне Java. Обеспечено 100% обнаружение кандидатов с номерами `+7 (999) 111-22-33`, `8-999-111-2233` и т.д.
3. **Реализация политики запрета дублирования карточек кандидатов**:
   - В мастере `SmartCvUploadScreen` при обнаружении существующего кандидата блок `duplicateBox` выдаёт подробное предупреждение с реквизитами найденного кандидата.
   - Основная кнопка действия переведена на **«Не дублировать (привязать резюме к кандидату)»** (`attachDuplicateBtn`, стиль `primary`). При нажатии сохраняется новая версия `CandidateCV` с привязкой к найденному кандидату без создания дубликата `JobCandidate`.
   - При попытке нажать «Дублировать (создать новую запись)» рекрутеру выводится модальное окно подтверждения с предупреждением о запрете дублирования в системе, где действие по умолчанию ориентировано на отказ от дублирования.
   - Если кандидат уникален, отображается кнопка **«Создать карточку кандидата»**.
4. **Устранение Дефекта 3 (Установка фокуса в таблицах реестров)**:
   В `JobCandidateReestr.java` и `CandidateCVReestrBrowse.java` фокус таблицы теперь устанавливается с извлечением инстанса сущности из перегруженного `CollectionContainer` (`jobCandidatesDc.getItemOrNull` и `candidateCVsDc.getItemOrNull`), гарантируя стабильную визуальную подсветку строки.
5. **Внедрение калиброванного системного промпта v3**:
   Создана миграция `260913-2-updateSmartCvParsePromptV3.xml` и подключена в `db.changelog-master.xml` (`CONFIGURATION_VERSION = 3`).
6. **Автоматизированное подтверждение**:
   Все 13 тестов в `SmartCvIngestComprehensiveTest` и контрактные тесты `SmartCvIngestServiceContractTest` успешно пройдены.
