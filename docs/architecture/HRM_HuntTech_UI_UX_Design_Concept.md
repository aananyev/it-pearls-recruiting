# Общая концепция UI/UX HRM HuntTech

> Каноническое имя: `HRM_HuntTech_UI_UX_Design_Concept.md`.  
> Область: экранные формы CUBA Platform 7.3.  
> Базовые референсы: `JobCandidateEdit`, `ExtSettingsWindow`.  
> Режим актуализации: документ **не обновляется автоматически**; изменения вносятся только по прямой команде Алексея и только для фактически реализованных принципов.

## Business & Context Intro

### Назначение и бизнес-смысл (What & Why)

Концепция определяет общий визуальный язык HRM HuntTech, чтобы пользователь воспринимал разные экранные формы как части одной системы. Единообразие уменьшает время поиска действий и полей, снижает риск ошибок при работе с рекрутинговыми данными и позволяет развивать интерфейс без изменения бизнес-логики.

Концепция не является разрешением на массовый редизайн. Для каждого экрана сохраняются его информационная архитектура, component ID, data binding, actions, loaders, views, JPQL и контроллеры. Визуальные решения адаптируются под фактический контекст формы.

### UI Context & Navigation

- `JobCandidateEdit` — основной референс сложной Edit-формы: тёмная постоянная панель слева, светлая рабочая область справа, toolbar, вкладки, карточки и локальные состояния компонентов.
- `ExtSettingsWindow` — референс формы персональных настроек: существующая четырёхвкладочная структура, двухпанельные разделы и локальный namespace `.ext-settings-window`.
- Новые формы используют эти принципы только после анализа существующей навигации и CUBA-контрактов.

### Behavior Summary

- открытие формы → загружаются штатные данные и actions → визуальный слой не инициирует запросы;
- изменение значения → работает существующий binding или контроллер → presentation не меняет данные;
- focus / hover / disabled / read-only → меняется локальное визуальное состояние → права, required и validators сохраняются;
- сохранение или отмена → выполняются прежние CUBA actions → визуальная унификация не вмешивается в lifecycle;
- изменение темы → используются локальные theme extension → геометрия и контраст сохраняются без глобальных селекторов.

## 1. Архитектура сложной формы

Сложная Edit-форма может использовать двухпанельную композицию, когда пользователю нужен постоянный контекст:

```text
тёмная фиксированная контекстная панель → светлая рабочая область с toolbar, вкладками и карточками
```

Двухпанельный layout не является обязательным шаблоном для каждого экрана. Его применение допустимо только без переноса полей между бизнес-разделами и без изменения навигационного контракта.

## 2. Визуальная иерархия

1. **Контекстная панель** — тёмная поверхность, постоянный контекст, профиль или назначение раздела, навигация и служебные подсказки.
2. **Рабочая область** — спокойный фон, отделяющий поверхность формы от карточек.
3. **Toolbar** — единая строка заголовка, пояснения и существующих действий.
4. **Вкладки** — крупная горизонтальная навигация с видимым активным состоянием.
5. **Карточки** — основной уровень группировки связанных полей.
6. **Заголовок секции** — выраженная типографика и стабильный интервал.
7. **Поясняющий текст** — вторичный цвет и читаемый межстрочный интервал.

Визуальная адаптация считается выполненной только тогда, когда различия видимы без анализа DOM и CSS. Простая замена рамки или тени при сохранении прежней светлой композиции не считается переносом дизайн-языка `JobCandidateEdit`.

## 3. Тёмная контекстная панель

Подтверждённый визуальный контракт сложной формы:

- базовый фон `#172638`;
- вертикальный градиент `#172638 → #132130 → #0f1b28`;
- основной текст `#f8fafc`;
- акцент заголовка и активной навигации `#ffb11b`;
- полупрозрачные внутренние карточки;
- правая граница и боковая тень;
- отсутствие скругления внешнего края панели;
- локальная адаптация ширины для viewport до 1366 px.

Контент панели адаптируется под экран. `JobCandidateEdit` показывает профиль кандидата, `ExtSettingsWindow` — назначение вкладки, профиль пользователя, индекс разделов и подсказки. Компоненты не копируются между формами.

## 4. Рабочая область

- фон рабочей области отделяется от карточек;
- toolbar имеет собственную поверхность и нижний визуальный ритм;
- вкладки располагаются на отдельной панели;
- контент прокручивается внутри рабочей области, а не вместе с контекстной панелью;
- контейнеры получают `min-width: 0`, когда это необходимо для корректного сжатия;
- структурный reflow не вводится одним SCSS, если он требует изменения XML-компоновки.

## 5. Вкладки

Подтверждённый паттерн:

- высота строки вкладок — 48 px;
- подпись — 15–16 px, насыщенность 600;
- активное состояние — цвет акцента и нижняя граница 3 px;
- hover меняет цвет, но не размеры;
- TabSheet сохраняет штатное поведение CUBA;
- все селекторы ограничены локальным корнем формы.

## 6. Карточки, toolbar и секции

- toolbar — минимальная высота 58 px;
- карточка — радиус 8 px;
- внутренний отступ карточки — преимущественно 16–22 px;
- тень карточки — `0 2px 8px rgba(15, 23, 42, 0.05)` или эквивалент для темы;
- заголовок карточки — около 18 px, насыщенность 700;
- заголовок toolbar — около 20 px, насыщенность 700;
- accordion-header визуально отделяется от содержимого;
- декоративные большие радиусы и тяжёлые web-тени не используются.

## 7. Поля ввода и состояния

Для `TextField`, `TextArea`, `LookupField`, `DateField` и совместимых компонентов:

- тип компонента, property, datasource/dataContainer, required и validators не меняются;
- однострочные поля имеют высоту около 38 px;
- размер текста — около 15–16 px;
- фон и рамка используют переменные темы;
- focus обозначается цветом `$v-selection-color` и внешним контуром 2 px;
- read-only отличается фоном, но остаётся читаемым;
- disabled имеет пониженную непрозрачность, при этом подпись не исчезает;
- caption визуально отделён от поля и имеет умеренную насыщенность.

## 8. Кнопки и панели действий

- существующие actions, `invoke`, captions, icons и enable-состояния сохраняются;
- primary используется только для уже существующего основного действия;
- danger используется только для существующего опасного действия;
- стандартная высота кнопки — 38–40 px;
- hover и focus задаются локально;
- toolbar не создаёт новые действия и не меняет порядок их выполнения;
- нижняя панель действий визуально отделяется от рабочей области.

## 9. Локальные namespaces

Каждая сложная форма имеет собственный корень:

```scss
.job-candidate-editor { ... }
.ext-settings-window { ... }
```

Запрещено:

- подключать `.job-candidate-editor` как зависимость другой формы;
- объявлять неограниченные `.v-button`, `.v-label`, `.v-table`, `.v-tabsheet`, `.v-textfield`;
- использовать общий selector для всех потомков экрана;
- менять глобальную тему ради одного экрана.

Допустимы вложенные Vaadin-селекторы только внутри локального корня формы.

## 10. Theme-aware оформление

Базовые переменные:

```scss
$v-app-background-color
$v-panel-background-color
$v-font-color
$v-selection-color
$v-border-radius
```

Тёмная контекстная панель является фирменной поверхностью и может использовать фиксированную палитру HRM HuntTech. Рабочая область, карточки, поля, captions, focus и read-only состояния используют переменные текущей темы.

Halo является обязательной эталонной проверкой. Тема `hover` является активной темой приложения по умолчанию. Остальные темы используют тот же структурный SCSS-контракт без изменения XML, component ID или поведения.

## 11. Подтверждённая реализация JobCandidateEdit

- тёмная профильная панель слева;
- светлая рабочая область;
- вкладки 48 px;
- toolbar 58 px;
- карточки с радиусом 8 px;
- поля 38 px;
- акцент `#ffb11b` в профильном контексте;
- локальный namespace `.job-candidate-editor`.

## 12. Подтверждённая реализация ExtSettingsWindow

На 2026-07-24 фактически применены:

- корневой namespace `.ext-settings-window`;
- тёмная контекстная панель на всех четырёх вкладках;
- градиент `#172638 → #132130 → #0f1b28`;
- акцент `#ffb11b` для заголовков и активной навигации sidebar;
- локальная стилизация `TabSheet` через `.ext-settings-tabs`;
- вкладки высотой 48 px;
- toolbar высотой не менее 58 px;
- карточки с радиусом 8 px и выраженной рамкой;
- поля высотой не менее 38 px;
- локальные focus, hover, disabled и read-only состояния;
- отсутствие зависимости от `.job-candidate-editor`;
- одинаковый SCSS-контракт для семи тем.

Структура четырёх вкладок `ExtSettingsWindow`, component ID, captions, bindings, actions, validators, контроллер и бизнес-логика не изменены.

## 13. Критерий приёмки визуальной адаптации

Визуальная задача считается завершённой только при одновременном выполнении условий:

1. новый CSS присутствует в развёрнутом `VAADIN/themes/*/styles.css`;
2. нужный root style присутствует в DOM;
3. браузерный cache отключён или выполнен hard reload;
4. визуальное отличие заметно на screenshot без инспектора;
5. smoke выполнен во всех заявленных темах;
6. компонентные и бизнес-контракты не изменены.

HTTP 200 и `BUILD SUCCESSFUL` без визуального smoke не подтверждают успешность UI-задачи.
