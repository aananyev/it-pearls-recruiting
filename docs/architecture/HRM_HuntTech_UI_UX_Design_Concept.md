# Общая концепция UI/UX HRM HuntTech

> Каноническое имя: `HRM_HuntTech_UI_UX_Design_Concept.md`.  
> Область: экранные формы CUBA Platform 7.3.  
> Статус: **основной обязательный документ для проектирования и редизайна будущих форм HRM HuntTech**.  
> Базовые референсы: `JobCandidateEdit`, `ExtSettingsWindow`.  
> Режим актуализации: документ **не обновляется автоматически**; изменения вносятся только по прямой команде Алексея и только для фактически реализованных и проверенных принципов.

## Business & Context Intro

### Назначение и бизнес-смысл (What & Why)

Концепция определяет общий визуальный язык HRM HuntTech, чтобы пользователь воспринимал разные экранные формы как части одной системы. Единообразие уменьшает время поиска действий и полей, снижает риск ошибок при работе с рекрутинговыми данными и позволяет развивать интерфейс без изменения бизнес-логики.

Документ является основной точкой отсчёта для любого будущего редизайна, визуального рефакторинга или адаптации экранной формы HRM HuntTech. До проектирования изменений необходимо сопоставить текущую форму с подтверждёнными паттернами концепции, определить применимые решения и зафиксировать обоснованные отклонения.

Концепция не является разрешением на массовый редизайн. Для каждого экрана сохраняются его информационная архитектура, component ID, data binding, actions, loaders, views, JPQL и контроллеры. Визуальные решения адаптируются под фактический контекст формы.

### UI Context & Navigation

- `JobCandidateEdit` — основной референс сложной Edit-формы: тёмная постоянная панель слева, светлая рабочая область справа, toolbar, вкладки, карточки, аккордеоны, профильное изображение и локальные состояния компонентов.
- `ExtSettingsWindow` — референс формы персональных настроек: существующая четырёхвкладочная структура, двухпанельные разделы, полноширинные вертикальные аккордеоны, круглый аватар с fallback и локальный namespace `.ext-settings-window`.
- Новые формы используют эти принципы только после анализа существующей навигации, доступной ширины, плотности данных и CUBA-контрактов.
- Спецификация конкретного экрана уточняет локальную компоновку, но не заменяет общую концепцию.

### Behavior Summary

- запрос на редизайн → анализируется этот документ и текущая UI-спецификация → выбираются подтверждённые паттерны без механического копирования формы;
- открытие формы → загружаются штатные данные и actions → визуальный слой не инициирует запросы;
- изменение значения → работает существующий binding или контроллер → presentation не меняет данные;
- раскрытие или сворачивание визуальной секции → меняется только видимость содержимого → данные, validation и сохранение не меняются;
- focus / hover / disabled / read-only → меняется локальное визуальное состояние → права, required и validators сохраняются;
- сохранение или отмена → выполняются прежние CUBA actions → визуальная унификация не вмешивается в lifecycle;
- изменение темы → используются локальные theme extension → геометрия и контраст сохраняются без глобальных селекторов;
- завершение редизайна → обновляется UI-спецификация экрана и выполняется visual smoke → концепция меняется только по отдельной прямой команде.

## 0. Обязательный порядок применения

Для каждого будущего редизайна, визуального рефакторинга или создания новой формы HRM HuntTech необходимо:

1. прочитать актуальную версию этого документа до изменения XML, Java или SCSS;
2. изучить текущие XML-дескрипторы, контроллеры, локальные стили, actions, bindings, views и UI-спецификацию формы;
3. определить, какие подтверждённые паттерны применимы к фактической задаче формы;
4. сначала проверить существующие компоненты, loaders, delegates и локальные стили HRM HuntTech;
5. назначить форме собственный локальный visual namespace;
6. сохранить component ID, captions, datasource/dataContainer, property, loaders, actions, `invoke`, JPQL, views и lifecycle, если пользователь прямо не разрешил их изменение;
7. описать в UI-спецификации применённые паттерны и причины отклонений;
8. синхронизировать все поддерживаемые темы и выполнить visual smoke;
9. не объявлять UI-задачу завершённой только по `BUILD SUCCESSFUL` и HTTP 200.

### Иерархия решений

При редизайне используется следующая иерархия:

1. прямое указание пользователя и утверждённые ограничения задачи;
2. существующие бизнес- и CUBA-контракты формы;
3. этот документ как основной стандарт визуальных и интеракционных решений;
4. UI-спецификация конкретного экрана как локальное уточнение;
5. фактически существующие компоненты и SCSS проекта.

Отклонение от концепции допустимо, если применение паттерна ухудшает бизнес-сценарий, нарушает доступную ширину, CUBA-контракт или читаемость. Причина отклонения фиксируется в UI-спецификации и PR.

## 1. Архитектура сложной формы

Сложная Edit-форма может использовать двухпанельную композицию, когда пользователю нужен постоянный контекст:

```text
тёмная фиксированная контекстная панель → светлая рабочая область с toolbar, вкладками, карточками и аккордеонами
```

Двухпанельный layout не является обязательным шаблоном для каждого экрана. Его применение допустимо только без переноса полей между бизнес-разделами и без изменения навигационного контракта.

Фиксированная sidebar не должна приводить к чрезмерному сжатию полей справа. Если полезная ширина недостаточна, приоритет имеют полноширинные вертикальные секции, уменьшение числа колонок или XML-reflow, а не уменьшение читаемости полей.

## 2. Визуальная иерархия

1. **Контекстная панель** — тёмная поверхность, постоянный контекст, профиль или назначение раздела, навигация и служебные подсказки.
2. **Рабочая область** — спокойный фон, отделяющий поверхность формы от карточек.
3. **Toolbar** — единая строка заголовка, пояснения и существующих действий.
4. **Вкладки** — крупная горизонтальная навигация с видимым активным состоянием.
5. **Карточки и аккордеоны** — основной уровень группировки связанных полей.
6. **Заголовок секции** — выраженная типографика и стабильный интервал.
7. **Поясняющий текст** — вторичный цвет и читаемый межстрочный интервал.

Визуальная адаптация считается выполненной только тогда, когда различия видимы без анализа DOM и CSS. Простая замена рамки или тени при сохранении прежней светлой композиции не считается переносом дизайн-языка `JobCandidateEdit`.

## 3. Тёмная контекстная панель

Подтверждённый визуальный контракт сложной формы:

- базовый фон `#172638`;
- вертикальный градиент `#172638 → #132130 → #0f1b28`;
- основной текст `#f8fafc`;
- акцент заголовка и активной навигации `#ffb11b`;
- полупрозрачные внутренние карточки;
- правая граница и боковая тень;
- отсутствие скругления внешнего края панели;
- локальная адаптация ширины для viewport до 1366 px.

Контент панели адаптируется под экран. `JobCandidateEdit` показывает профиль кандидата, `ExtSettingsWindow` — назначение вкладки, профиль пользователя, индекс разделов и подсказки. Компоненты не копируются между формами.

## 4. Рабочая область

- фон рабочей области отделяется от карточек;
- toolbar имеет собственную поверхность и нижний визуальный ритм;
- вкладки располагаются на отдельной панели;
- контент прокручивается внутри рабочей области, а не вместе с контекстной панелью;
- контейнеры получают `min-width: 0`, когда это необходимо для корректного сжатия;
- структурный reflow не вводится одним SCSS, если он требует изменения XML-компоновки;
- минимальная полезная ширина поля важнее сохранения формального числа колонок;
- горизонтальная прокрутка основной формы рассматривается как дефект, если не обусловлена таблицей или иным специализированным компонентом.

## 5. Вкладки

Подтверждённый паттерн:

- высота строки вкладок — 48 px;
- подпись — 15–16 px, насыщенность 600;
- активное состояние — цвет акцента и нижняя граница 3 px;
- hover меняет цвет, но не размеры;
- TabSheet сохраняет штатное поведение CUBA;
- все селекторы ограничены локальным корнем формы.

## 6. Карточки, toolbar и секции

- toolbar — минимальная высота 58 px;
- карточка — радиус 8 px;
- внутренний отступ карточки — преимущественно 16–22 px;
- тень карточки — `0 2px 8px rgba(15, 23, 42, 0.05)` или эквивалент для темы;
- заголовок карточки — около 18 px, насыщенность 700;
- заголовок toolbar — около 20 px, насыщенность 700;
- accordion-header визуально отделяется от содержимого;
- декоративные большие радиусы и тяжёлые web-тени не используются.

### 6.1. Когда использовать карточки

Карточка используется, когда:

- группа компактна и должна быть постоянно видимой;
- одновременное сравнение с соседними группами важно;
- содержимое помещается без чрезмерного сжатия;
- скрытие группы увеличит число лишних действий пользователя;
- группа представляет самостоятельный итог, статус, сводку или короткий набор полей.

### 6.2. Когда использовать вертикальные аккордеоны

Полноширинный вертикальный аккордеон используется, когда:

- несколько однотипных групп содержат подробные поля;
- фиксированная sidebar уменьшает доступную ширину рабочей области;
- многоколоночная сетка делает поля узкими или создаёт горизонтальную прокрутку;
- пользователю обычно нужна одна группа за раз;
- требуется progressive disclosure без изменения бизнес-логики.

Правила аккордеона:

- секции располагаются вертикально и занимают 100% полезной ширины;
- основная или наиболее часто используемая секция раскрывается по умолчанию;
- дополнительные секции могут быть свёрнуты;
- сворачивание меняет только presentation и не очищает значения;
- loaders, validation, required, datasource и сохранение продолжают работать независимо от collapsed-состояния;
- Java-обработчики раскрытия не добавляются без функциональной необходимости;
- существующий `GroupBoxLayout` и локальные стили переиспользуются прежде, чем создаётся новый компонент.

## 7. Поля ввода и состояния

Для `TextField`, `TextArea`, `LookupField`, `DateField` и совместимых компонентов:

- тип компонента, property, datasource/dataContainer, required и validators не меняются;
- однострочные поля имеют высоту около 38 px;
- размер текста — около 15–16 px;
- фон и рамка используют переменные темы;
- focus обозначается цветом `$v-selection-color` и внешним контуром 2 px;
- read-only отличается фоном, но остаётся читаемым;
- disabled имеет пониженную непрозрачность, при этом подпись не исчезает;
- caption визуально отделён от поля и имеет умеренную насыщенность.

## 8. Кнопки и панели действий

- существующие actions, `invoke`, captions, icons и enable-состояния сохраняются;
- primary используется только для уже существующего основного действия;
- danger используется только для существующего опасного действия;
- стандартная высота кнопки — 38–40 px;
- hover и focus задаются локально;
- toolbar не создаёт новые действия и не меняет порядок их выполнения;
- нижняя панель действий визуально отделяется от рабочей области.

## 9. Локальные namespaces

Каждая сложная форма имеет собственный корень:

```scss
.job-candidate-editor { ... }
.ext-settings-window { ... }
```

Запрещено:

- подключать `.job-candidate-editor` как зависимость другой формы;
- объявлять неограниченные `.v-button`, `.v-label`, `.v-table`, `.v-tabsheet`, `.v-textfield`;
- использовать общий selector для всех потомков экрана;
- менять глобальную тему ради одного экрана.

Допустимы вложенные Vaadin-селекторы только внутри локального корня формы.

## 10. Theme-aware оформление

Базовые переменные:

```scss
$v-app-background-color
$v-panel-background-color
$v-font-color
$v-selection-color
$v-border-radius
```

Тёмная контекстная панель является фирменной поверхностью и может использовать фиксированную палитру HRM HuntTech. Рабочая область, карточки, поля, captions, focus и read-only состояния используют переменные текущей темы.

Halo является обязательной эталонной проверкой. Тема `hover` является активной темой приложения по умолчанию. Остальные темы используют тот же структурный SCSS-контракт без изменения XML, component ID или поведения.

## 11. Профильные изображения и fallback

Для круглых фотографий кандидатов и пользователей используется существующий компонент `OvaFallbackImage`, если экрану одновременно нужны:

- круглое или овальное отображение;
- стабильный размер;
- theme fallback при отсутствии значения или файла;
- совместимость с базовым CUBA `Image`.

Фактические legacy-идентификаторы проекта:

- Java-контракт: `OvaFallbackImage`;
- XML-тег: `<ovaFallbackImage>`;
- Web-реализация: `WebOvaFallbackImage`.

Имя `OvaFallbackImage` не исправляется на `OvalFallbackImage`, поскольку связано с регистраторами, loader, XML и существующими тестами.

Правила применения:

- сохранять существующий component ID, datasource/dataContainer, property и upload-контракт;
- задавать `ovalWidth` и `ovalHeight` явно для профильного изображения;
- использовать `SCALE_DOWN` или другой режим, исключающий искажение фотографии;
- задавать `fallbackThemePath` через существующий theme-ресурс;
- не создавать пару независимых компонентов для фотографии и placeholder, если существующая логика экрана позволяет безопасно использовать единый fallback-компонент;
- если legacy-контроллер уже переключает отдельный `defaultPic`, переход выполняется без изменения Java только при подтверждённой совместимости;
- проверять наличие и качество fallback во всех поддерживаемых темах.

Конкретный размер определяется экраном. Подтверждённый размер профильного изображения в `JobCandidateEdit` и вкладке «Обо мне» `ExtSettingsWindow` — 176×176 px.

## 12. Повторное использование компонентов и стилей

Перед созданием нового UI-компонента, loader, delegate или SCSS-блока необходимо проверить существующие реализации HRM HuntTech.

Приоритет:

1. существующий компонент с подходящим контрактом;
2. существующий локальный стиль или mixin внутри namespace формы;
3. композиция существующих компонентов;
4. новый локальный компонент или стиль, только если первые варианты не покрывают задачу.

Запрещено создавать почти идентичные компоненты только ради другого имени или экрана. Повторное использование не означает зависимость от namespace другой формы: общая логика выносится в компонент или mixin, а экран сохраняет собственный корневой namespace.

## 13. Подтверждённая реализация JobCandidateEdit

- тёмная профильная панель слева;
- светлая рабочая область;
- вкладки 48 px;
- toolbar 58 px;
- карточки и секции-аккордеоны;
- карточки с радиусом 8 px;
- поля 38 px;
- акцент `#ffb11b` в профильном контексте;
- `OvaFallbackImage` для круглого изображения кандидата;
- локальный namespace `.job-candidate-editor`.

## 14. Подтверждённая реализация ExtSettingsWindow

На 2026-07-25 фактически применены:

- корневой namespace `.ext-settings-window`;
- тёмная контекстная панель на всех четырёх вкладках;
- градиент `#172638 → #132130 → #0f1b28`;
- акцент `#ffb11b` для заголовков и активной навигации sidebar;
- локальная стилизация `TabSheet` через `.ext-settings-tabs`;
- вкладки высотой 48 px;
- toolbar высотой не менее 58 px;
- карточки с радиусом 8 px и выраженной рамкой;
- поля высотой не менее 38 px;
- полноширинные вертикальные аккордеоны SMTP, POP3 и IMAP вместо сжатой трёхколоночной сетки;
- SMTP раскрыта по умолчанию, POP3 и IMAP свёрнуты;
- `OvaFallbackImage` 176×176 px для фотографии пользователя во вкладке «Обо мне»;
- локальные focus, hover, disabled и read-only состояния;
- отсутствие зависимости от `.job-candidate-editor`;
- повторное использование существующих компонентов и стилей;
- одинаковый SCSS-контракт для семи тем.

Структура четырёх вкладок `ExtSettingsWindow`, legacy component ID, captions, bindings, actions, validators, контроллер и бизнес-логика сохранены. Визуальные аккордеоны не изменяют порядок загрузки и сохранения почтовых значений.

## 15. Критерий приёмки визуальной адаптации

Визуальная задача считается завершённой только при одновременном выполнении условий:

1. новый CSS присутствует в развёрнутом `VAADIN/themes/*/styles.css`;
2. нужный root style присутствует в DOM;
3. браузерный cache отключён или выполнен hard reload;
4. визуальное отличие заметно на screenshot без инспектора;
5. smoke выполнен во всех заявленных темах;
6. карточки и аккордеоны не создают чрезмерного сжатия или необоснованной горизонтальной прокрутки;
7. профильные изображения и fallback отображаются с подтверждённой геометрией;
8. component ID, bindings, actions, validators и бизнес-контракты сохранены;
9. UI-спецификация экрана синхронизирована;
10. отклонения от концепции явно обоснованы.

HTTP 200 и `BUILD SUCCESSFUL` без visual smoke не подтверждают успешность UI-задачи.
