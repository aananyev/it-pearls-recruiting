# Архитектура ускорения JobCandidateEdit в HRM HuntTech

## Business & Context Intro

### 1. Назначение и Бизнес-смысл (What & Why)

`JobCandidateEdit` — центральная рабочая карточка кандидата. Скорость её первого отображения напрямую влияет на ежедневную производительность рекрутеров, потому что экран открывается многократно и объединяет основные сведения, контакты, взаимодействия, резюме, вакансии, комментарии и вспомогательные данные.

Цель архитектурного решения — показывать редактируемую карточку как можно раньше, сохраняя весь существующий бизнес-контракт, а тяжёлые и редко используемые данные подгружать только тогда, когда они действительно понадобились пользователю.

### 2. Связи в интерфейсе и Навигация (UI Context & Navigation)

Экран открывается из `JobCandidateBrowse`, HR-Мастера и связанных рекрутинговых сценариев. Основная вкладка `tabMain` должна быть полностью готова к редактированию сразу после открытия. Остальные вкладки используют существующий `tabSheetSocialNetworks` и сохраняют текущие ID, действия, контейнеры и сценарии навигации.

Архитектура не меняет:

- ID экрана `hunttech_JobCandidate.edit`;
- component ID и data bindings;
- действия сохранения, отмены, lookup/open/create;
- `DataContext` редактируемого кандидата;
- бизнес-правила и валидацию;
- состав доступных пользователю данных.

### 3. Краткий обзор бизнес-логики поведения (Behavior Summary)

- Открытие карточки → загружается только минимальный граф основной вкладки → форма сразу доступна пользователю.
- Первое открытие дополнительной вкладки → выполняется её узкий loader → результат помещается в соответствующий контейнер и `DataContext`.
- Отображение read-only показателей → экран уже показан → вычисления выполняются асинхронно → UI обновляется только в `done()` на UI-потоке.
- Повторное открытие вкладки → ранее загруженные данные используются повторно → лишний SQL не выполняется.
- Закрытие экрана → связанные фоновые задачи отменяются → результат не применяется к закрытому UI.
- Сохранение → все редактируемые данные остаются в штатном `DataContext` → применяется существующий commit-сценарий CUBA.

## 2. Текущее состояние загрузки

### 2.1. Основной entity view

Текущий inline view `jobCandidateDc` вместе с полями основной карточки включает коллекции:

- `positionList`;
- `iteractionList` с вакансией, проектом и типом взаимодействия;
- `socialNetwork`;
- `candidateCv` с вакансией, проектом, описанием, логотипом и подразделением.

При наличии `@LoadDataBeforeShow` этот граф участвует в первоначальной загрузке редактора. Одновременно контроллер содержит отдельные методы `ensureInteractionsLoaded()`, `ensureCandidateCvLoaded()` и `ensureSocialNetworksLoaded()`, которые предназначены для загрузки при первом открытии вкладки. Пока коллекции присутствуют в стартовом view, ленивый слой не даёт полного эффекта и может повторно загружать уже полученные данные.

### 2.2. Вспомогательные справочники

В XML присутствуют loaders полного списка компаний, городов и должностей. Для компаний уже реализован `SuggestionPickerField` с серверным `SearchExecutor` и `maxResults(50)`, поэтому предварительная загрузка всего справочника компаний не требуется для обычного ввода.

Для городов и должностей loaders уже защищены от автоматической загрузки до инициализации основной вкладки. Аналогичную политику следует применить ко всем необязательным loaders.

### 2.3. Комментарии

`interactionCommentDl` использует условие с параметром `candidate`. В CUBA условие loader добавляется в запрос только при наличии всех параметров. Поэтому loader должен быть явно заблокирован до установки кандидата и запускаться только из `initTabComments()`; иначе существует риск выполнения более широкой выборки.

### 2.4. Уже используемые фоновые задачи

Контроллер уже применяет `BackgroundTask` для анализа навыков и агрегации истории позиций. Это правильное направление, если рабочий поток получает только UUID/скалярные параметры, не изменяет UI и контейнеры, а результат применяется в `done()`.

## 3. Целевая модель: Progressive Data Hydration

Рекомендуемый паттерн — двухфазная прогрессивная загрузка данных.

```text
Фаза A. Critical path
    минимальный JobCandidate view
    + основная вкладка
    + обязательные actions/listeners
    ↓
    экран отображён и доступен для ввода

Фаза B. On-demand / after-show
    read-only summary после показа
    + данные вкладки при первом открытии
    + необязательный idle-prefetch первой страницы
```

Ключевой принцип: в critical path остаётся только то, без чего пользователь не может начать работу на `tabMain`.

## 4. Рекомендуемые архитектурные изменения

### 4.1. P0 — полностью исключить необязательные автозагрузки

Сохранить `@LoadDataBeforeShow` для редактируемой сущности, но заблокировать через `PreLoadEvent.preventLoad()` каждый необязательный loader до явной готовности:

- `currentCompaniesLc`;
- `interactionCommentDl`;
- loaders тяжёлых вкладок;
- loaders подходящих и открытых вакансий;
- любые справочники, которые не нужны для первого paint.

Запускать loader только из метода инициализации соответствующей вкладки после установки параметров.

**Ожидаемый эффект:** устранение лишних SQL-запросов и случайных широких выборок без изменения UI-контрактов.

**Риск:** низкий.

### 4.2. P0 — использовать поиск вместо полного списка компаний

Для `currentCompanyField` оставить существующий `SearchExecutor` и не загружать `currentCompaniesLc` целиком.

Рекомендуемые параметры:

```xml
minSearchStringLength="2"
asyncSearchDelayMs="300"
suggestionsLimit="30"
```

Созданная через действие `createCompany` компания добавляется только в локальный контейнер текущего экрана и сразу устанавливается в поле.

**Ожидаемый эффект:** отсутствие полной выборки компаний и уменьшение сериализации.

**Риск:** низкий при сохранении `picker_lookup`, `picker_open`, `picker_clear` и `createCompany`.

### 4.3. P1 — выделить минимальный стартовый view

Создать отдельный view, например:

```text
jobCandidate-open-view
```

В него включить только поля, используемые на основной вкладке и в sidebar:

- локальные поля `JobCandidate`;
- `cityOfResidence`;
- `currentCompany` с минимальным picker-view;
- `personPosition`;
- `fileImageFace`;
- небольшую `positionList`, только если она действительно отображается при открытии.

Исключить из стартового view:

- `iteractionList`;
- `candidateCv`;
- `socialNetwork`;
- тяжёлые вложенные графы вакансий и проектов;
- тексты резюме, письма и бинарные данные.

Каждую коллекцию загружать отдельным loader/DataManager-запросом при первом открытии вкладки с узким view.

**Ожидаемый эффект:** максимальное уменьшение entity-графа, памяти Web Client и объёма сериализации для кандидатов с большой историей.

**Риск:** средний. Необходимо проверить каждый getter контроллера через Data View Integrity и корректно объединять данные с `DataContext`.

### 4.4. P1 — настоящее ленивое открытие вкладок

Для каждой вкладки использовать одинаковый state machine:

```text
NOT_LOADED → LOADING → LOADED
                 ↘ ERROR → повторная попытка
```

Рекомендуемое поведение:

| Вкладка | Способ загрузки |
|---|---|
| Взаимодействия | узкий view, сортировка от новых к старым, первая страница |
| Резюме | метаданные CV без LOB; полный `textCV` только при открытии/анализе конкретного CV |
| Контакты и соцсети | отдельный loader при первом открытии |
| Комментарии | параметр кандидата + первая страница |
| Позиции и вакансии | существующая фоновая скалярная агрегация |

Редактируемые коллекции следует загружать на UI-потоке штатным loader с `DataContext`. В фон выносится только read-only вычисление или подготовка DTO, но не изменение detached entity-графа.

### 4.5. P1 — отложенный read-only summary после показа

После `AfterShowEvent` можно асинхронно загрузить один компактный DTO:

```text
JobCandidateOpenSummary
- hasCv
- averageRating
- lastInteractionId
- lastInteractionDate
- lastInteractionCaption
- interactionCount
- cvCount
```

Реализация:

- `run()` получает только `candidateId`;
- использует `DataManager.loadValue()`/`loadValues()` либо middleware-сервис;
- не обращается к UI и контейнерам;
- `done()` устанавливает labels и indicators;
- задача связана с экраном и отменяется при закрытии.

Это позволяет убрать из синхронного `onBeforeShow` рейтинг и последнее взаимодействие. По ранее полученному профилю выигрыш на сервере будет измеряться десятками миллисекунд, поэтому это не основной, но безопасный этап.

### 4.6. P1 — пагинация тяжёлых коллекций

Не загружать всю историю кандидата за один раз. Для взаимодействий, комментариев и CV:

- сортировать от новых к старым;
- загружать первые 50–100 строк;
- использовать paging/load more;
- сохранять возможность получить полную историю по запросу пользователя.

**Ожидаемый эффект:** стабильное время открытия вкладки независимо от возраста и насыщенности карточки.

### 4.7. P2 — пересмотреть Entity Cache и Query Cache

Кэшировать следует маленькие и относительно стабильные справочники, а не крупные изменяемые графы кандидата.

Рекомендуемый аудит:

| Сущность | Рекомендация |
|---|---|
| `Position`, `City`, `Country`, типы взаимодействий, типы соцсетей | кандидат на entity cache с размером не меньше рабочего набора |
| `Company` | поиск по строке; не использовать полную cacheable-выборку без доказанной пользы |
| `JobCandidate` | проверить необходимость shared cache; высокоизменяемая сущность |
| `CandidateCV` | сильный кандидат на отключение shared cache из-за LOB и `byte[]` |
| `IteractionList` | не кэшировать большие пользовательские коллекции как справочник |

Важно: CUBA указывает, что для кэшируемой сущности `DataManager` может загружать все локальные атрибуты, даже если view узкий. Для `CandidateCV`, содержащей `textCV`, `letter`, `commentLetter` и `imageByteArray`, это может свести на нет частичную загрузку.

Query Cache применять только совместно с Entity Cache и только для запросов с высокой повторяемостью и низкой изменчивостью. Полные запросы компаний, кандидатов и взаимодействий не должны кэшироваться автоматически только ради ускорения одного экрана.

### 4.8. P2 — короткий predictive prefetch

После первого отображения и только при отсутствии активной работы пользователя можно предварительно загрузить первую страницу наиболее вероятной следующей вкладки, например взаимодействий.

Ограничения:

- только read-only DTO или ID;
- короткий TTL 30–60 секунд;
- ключ `candidateId + version`;
- отмена при закрытии экрана;
- не префетчить все вкладки;
- не переносить редактируемые сущности между потоками.

Prefetch является дополнением к ленивой загрузке, а не её заменой.

### 4.9. Долгие независимые операции

Парсинг CV, AI-анализ, генерация документов и массовые операции можно вынести в middleware task/job с отдельным статусом выполнения. Для обычного открытия редактора отдельные OS-процессы не рекомендуются: они усложняют консистентность, отмену и обработку ошибок. Для UI-сценария достаточно `BackgroundTask`, а для длительных устойчивых операций — серверной очереди задач.

## 5. Почему не следует переносить всё в параллельные потоки

Параллельная загрузка нескольких entity-графов не гарантирует ускорения:

- запросы конкурируют за пул соединений и CPU БД;
- результаты всё равно нужно последовательно применить к Vaadin UI;
- `DataContext` и UI нельзя безопасно изменять из фонового потока;
- пользователь часто не открывает большинство вкладок;
- параллельная загрузка увеличивает память и создаёт ненужную работу.

Поэтому предпочтение отдаётся последовательности:

```text
минимальный critical path
→ экран показан
→ on-demand loading
→ ограниченный idle-prefetch
```

## 6. Приоритетный план реализации

| Этап | Изменение | Ожидаемый эффект | Риск |
|---|---|---|---|
| A | Guard для всех необязательных loaders, особенно comments/company | исключение лишних SQL | низкий |
| B | Полностью отказаться от preload компаний в пользу SuggestionPickerField | меньше данных и памяти | низкий |
| C | `jobCandidate-open-view` без CV/interactions/socialNetwork | максимальный эффект на тяжёлых кандидатах | средний |
| D | Узкие loaders вкладок + пагинация | стабильное время вкладок | средний |
| E | `JobCandidateOpenSummary` после `AfterShowEvent` | убрать десятки ms из critical path | низкий |
| F | Аудит entity/query cache | исключить загрузку LOB и cache thrashing | средний |
| G | Опциональный idle-prefetch | ускорить вероятную следующую вкладку | средний |

Каждый этап выполняется отдельным коммитом с точкой отката и обязательным обновлением этой спецификации.

## 8. Контроль качества

Для каждого этапа обязательны:

```bash
git diff --check
./gradlew :app-web:compileJava --no-daemon --stacktrace
./gradlew test --tests '*ScreenViewIntegrityTest*' --no-daemon --stacktrace
./gradlew :app-web:buildScssThemes --no-daemon --stacktrace
./gradlew clean assemble --no-daemon --stacktrace
```

Если меняются view и контроллер:

- все getters контроллера должны входить в соответствующий view;
- нельзя читать незагруженный атрибут detached entity;

- HTTP 200 `/hrm`;
- новый кандидат;

- сохранение и отмена;

## 9. Критерии архитектурной готовности

Решение считается завершённым, когда:

- при первом открытии выполняется только запрос редактируемого кандидата и необходимые компактные summary-запросы;
- SQL дополнительных вкладок отсутствует до их первого открытия;
- полный список компаний не загружается при открытии формы;
- LOB-поля CV не загружаются до обращения к конкретному резюме;
- повторное открытие вкладки не выполняет повторную загрузку без явного refresh;
- фоновые задачи не обращаются к UI/DataContext из `run()`;
- закрытие экрана отменяет связанные задачи;
- бизнес-функциональность подтверждена smoke-test и интеграционными тестами.

## 10. Источники и основания

Архитектура основана на официальной документации CUBA Platform:

- Screen lifecycle: `BeforeShowEvent` и `AfterShowEvent`;
- data loaders, `PreLoadEvent`, `PostLoadEvent` и `@LoadDataBeforeShow`;
- views, частичные сущности и FetchGroup;
- `BackgroundTask`, `BackgroundWorker` и правила доступа к UI;
- `SuggestionPickerField` и асинхронный `SearchExecutor`;
- Entity Cache, Query Cache и статистика сущностей;
- `DataManager.loadValue()` и `loadValues()` для скалярных проекций.

Используемые принципы совпадают с общепринятыми практиками enterprise UI: минимизация critical path, progressive hydration, on-demand loading, ограниченный cache-aside и отказ от передачи изменяемых entity-графов между потоками.
