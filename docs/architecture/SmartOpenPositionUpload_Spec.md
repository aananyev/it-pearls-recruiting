## 1. Business & Context Intro

### 1.1. Бизнес-цель
Визард «Умная AI-загрузка и открытие вакансии» предназначен для ускоренного ввода и структурирования вакансий в HRM HuntTech из внешних источников:
1. Текстовое описание из мессенджеров, заявок клиентов или порталов (включая SSP Soft `need.ssp-soft.com`);
2. Файлы документов (PDF, DOCX, DOC, RTF, TXT);
3. Прямые ссылки на веб-страницы описания вакансии.

### 1.2. Пользовательский сценарий
Рекрутер или аккаунт-менеджер нажимает кнопку **«Умная загрузка»** (`smartUploadBtn`) на командном тулбаре экрана `OpenPositionReestrBrowse` (Реестр открытых позиций). Открывается диалог визарда, где пользователь передает текст или файл. AI-сервис (или fallback-парсер) структурирует данные, заполняет карточку предпросмотра, проверяет существующие дубликаты и выявляет отсутствующие обязательные поля. После подтверждения создается черновик вакансии (`OpenPosition`), который **гарантированно скрыт от внешней публикации на сайте**, пока ответственный рекрутер не проверит карточку и явно не снимет признак черновика.

## 3. Схема статуса «Черновик» и приоритетов (Разрешение расхождений)

### 3.1. Анализ исторического расхождения
- **Требование бизнеса**: Создаваемая визардом вакансия обязана иметь статус «Черновик» (`signDraft = true`) и не попадать в публичный REST-эндпоинт (`openPositionPublic`), пока рекрутер не проверит данные.
- **Прежнее поведение в коде**: Метод `createOpenPosition` выставлял `signDraft = false`, а скрытие от сайта осуществлялось исключительно за счет `priority = -2` (`UNDER_REVIEW`). При этом в UI `OpenPositionEdit` чекбокс `signDraftCheckBox` оставался снятым, бейдж в сайдбаре показывал «ОТКРЫТА» вместо «ЧЕРНОВИК», что вводило пользователя в заблуждение и не обеспечивало блокировки полей.

### 3.2. Архитектурное решение (Эшелонированная защита)
1. **Канонический атрибут черновика**:  
   `openPosition.setSignDraft(true);`
   - Сайдбар карточки `OpenPositionEdit` отображает статус **«ЧЕРНОВИК»** (`h3-gray`).
   - Чекбокс `signDraftCheckBox` отмечен `true`, выводится метка `(DRAFT)`.
   - В REST-запросе `openPositionPublic` условие `(e.signDraft is null or e.signDraft = false)` гарантированно исключает вакансию.
2. **Дополнительный статус проверки**:  
   `openPosition.setPriority(OpenPositionPriority.UNDER_REVIEW.getId()); // -2`
   - Служит дополнительным барьером: даже при непреднамеренном сбросе флага `signDraft` вакансия не опубликуется без смены приоритета на рабочий (`NORMAL = 2` или иной).
3. **Процесс публикации**:
   - Рекрутер открывает созданную вакансию в `OpenPositionEdit`.
   - Снимает чекбокс `signDraftCheckBox`:
     - `signDraft` переходит в `false`;
     - `priority` сбрасывается или рекрутер задает рабочий приоритет (по умолчанию `NORMAL = 2`);
   - После сохранения (`Commit`) вакансия немедленно становится доступна в `openPositionPublic`.

### 3.3. Согласованность с ботом `HunttechOpenCloseBot`
В боте (`hunttech_recruiting_bot/services/hrm.py`):
- Поддерживаются поля `open_close` (boolean) и `sign_draft` (boolean);
- Приоритеты: `-1 Draft`, `0 Пауза`, `1 Низкий`, `2 Нормальный`, `3 Высокий`, `4 Критический`.
Установка `signDraft = true` полностью согласована с логикой бота и контрактом базы данных.

## 4. Анти-дубликаты и диалоги нехватки данных

### 4.1. Анти-дубликаты вакансий (`findDuplicate`)
Перед созданием вакансии вызывается `smartOpenPositionIngestService.findDuplicate(parsedData)`:
- Поиск выполняется по нормализованному наименованию `vacansyName` среди активных вакансий (`openClose = false`);
- При обнаружении дубликата:
  - В UI визарда выводится предупреждающий блок `duplicateBox` с ID и именем существующей позиции;
  - При попытке нажать «Открыть позицию» пользователю показывается диалог подтверждения: продолжить создание дубля или перейти к существующей вакансии.

### 4.2. Защита от дублей и «тихих подстановок» сопутствующих сущностей
1. **Проект (`Project`)**:
   - **Запрет тихого дефолта**: Прежняя логика автоматически брала последний созданный в системе проект (`order by createTs desc`), если имя проекта в вакансии не распознано. Это приводило к ошибочной привязке вакансий к чужим проектам.
   - **Новое правило**: Если проект не указан или не найден по имени/компании, визард требует от пользователя подтверждения / выбора проекта, либо создает системный проект «Нераспределенные вакансии (Умная загрузка)».
2. **Тип позиции (`Position`)**:
   - Поиск по `positionRuName` и `positionEnName` без учета регистра.
   - Ограничение длины колонки: строго `truncate(cleanName, 80)`.
   - Если точного совпадения нет — создается только при наличии осмысленного названия (длина $\ge 3$ символов).
3. **Город (`City`) и Грейд (`Grade`)**:
   - Нечеткий поиск `like lower(:name)`.
   - При отсутствии данных поле остается `null` (не придумывать несуществующие города/грейды).

## 5. Точки расширения («Как корректировать»)

1. **Добавление нового формата / источника парсинга**:
   - В интерфейсе `SmartOpenPositionIngestService` расширяется метод извлечения текста `extractTextFromFile` или добавляется адаптер `extractTextFromUrl(String url)`.
   - В UI `SmartOpenPositionUploadScreen` добавляется вкладка / кнопка источника.
2. **Добавление обязательных полей для вакансий заказчиков (например, SSP Soft)**:
   - В `SmartOpenPositionParsedData` добавляются типизированные геттеры/сеттеры (например, `accountManager`, `workFormatDetails`, `slaDays`).
   - В AI-промпт `FUNCTION_VACANCY_SMART_PARSE_JSON` добавляются соответствующие ключи JSON схемы.
   - В `SmartOpenPositionIngestServiceBean.createOpenPosition` добавляется перенос полей в атрибуты сущности `OpenPosition`.
   - В `modules/core/test/...` обновляется `OpenPositionRestQueriesContractTest` и компонентные тесты создания вакансии.
