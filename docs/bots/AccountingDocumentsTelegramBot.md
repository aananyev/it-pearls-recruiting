# AccountingDocumentsTelegramBot — бухгалтерская первичка и авансовые отчеты

> Отдельный Telegram-бот бухгалтерского контура работает в Hermes, принимает сканы бухгалтерских документов, подтверждает раскладку, использует AI API Hermes, хранит метаданные в HRM HuntTech, раскладывает файлы в Yandex.Disk и отправляет бухгалтеру через Yandex.Mail.

## Business & Context Intro

### Назначение и бизнес-смысл (What & Why)

Бот автоматизирует ручной процесс передачи бухгалтеру бумажной первичной документации, сканов и чеков авансового отчета. Пользователь сканирует документ телефоном и отправляет его в отдельный Telegram-бот Hermes, а бот распознает документ через AI API Hermes, предлагает классификацию, после подтверждения раскладывает файл в Yandex.Disk и отправляет бухгалтеру по расписанию.

Цель процесса — исключить ручное переименование, поиск папки клиента, забытые документы, повторную отправку и смешивание первички с авансовыми отчетами. HRM HuntTech хранит реестр документов, статусы, события и связи со справочниками, а Yandex.Disk остается физическим архивом файлов.

Бухгалтерский бот не связан со встроенным Telegram-ботом HRM HuntTech. Встроенный HRM-бот продолжает обслуживать HRM-команды, а бухгалтерский Telegram runtime, подтверждения и AI/OCR выполняются в Hermes.

Строгое правило безопасности: бот не имеет права трогать, удалять, переименовывать, перезаписывать или перемещать уже существующие деловые документы на Yandex.Disk и локальном диске: акты, договоры, УПД, счета, задания, чеки и другие файлы клиентского или бухгалтерского архива. Автоматизация работает только с новыми файлами, которые пользователь отправил самому боту и которые бот сохранил во входящую зону.

### UI Context & Navigation

На первом этапе отдельный экран в HRM HuntTech не требуется. Основной пользовательский интерфейс — отдельный Telegram-бот Hermes с карточками подтверждения и inline-кнопками.

Входные точки:

- отправка фото или PDF в Telegram-бот;
- пересылка вложенного документа в Telegram-бот;
- ручной выбор команды бота для просмотра неразобранных документов, документов к отправке и ошибок.

Хранилища:

- входящие сканы: `/Users/alekseyananyev/Yandex.Disk-alan@hunttech.ru.localized/ХантТек/Сканы`;
- клиентские документы: `/Users/alekseyananyev/Yandex.Disk-alan@hunttech.ru.localized/ХантТек/Договоры/Клиенты`;
- авансовые отчеты: `/Users/alekseyananyev/Yandex.Disk-alan@hunttech.ru.localized/ХантТек/Бухгалтерия/Авансовые отчеты`.

Будущий UI в HRM HuntTech может быть добавлен поверх тех же сущностей: входящие, ожидающие подтверждения, готовые к отправке, отправленные, ошибки и журнал событий.

### Behavior Summary

| Действие | Условие | Результат |
| --- | --- | --- |
| Пользователь отправил документ в Telegram | файл является фото или PDF | бот сохраняет оригинал во входящую папку и создает запись реестра |
| OCR/AI распознал первичку | найден тип документа и клиент | бот отправляет карточку подтверждения |
| OCR/AI распознал чек | найден чек авансового отчета | бот предлагает дату, категорию, сумму и организацию |
| Пользователь подтвердил первичку | клиент найден в `Company` | файл переименован, перемещен в папку клиента и готов к дневной отправке |
| Пользователь подтвердил чек | категория и сумма подтверждены | файл переименован и помещен в папку месяца `К отправке` |
| Наступило время дневной отправки | есть подтвержденная первичка | бот отправляет отдельное письмо бухгалтеру через Yandex.Mail |
| Наступили последние числа месяца | есть чеки авансового отчета к отправке | бот отправляет отдельное письмо с фразой `Авансовый отчет` в теме |
| Контрагент не найден | OCR-название не сопоставилось с `Company` | документ остается в неразобранных и ждет ручного выбора компании |
| Письмо успешно отправлено | Yandex.Mail вернул успешный результат | документы получают статус `SENT`, чеки перемещаются в `Отправлено` |

## 1. Архитектура процесса

```text
Telegram
→ прием файла Hermes-ботом
→ входящая папка Yandex.Disk
→ OCR/AI распознавание через AI API Hermes
→ сопоставление со справочниками HRM HuntTech
→ Telegram-подтверждение
→ раскладка по папкам Yandex.Disk
→ ежедневная или месячная отправка через Yandex.Mail
→ запись событий в HRM HuntTech
```

Файлы физически не хранятся в базе HRM HuntTech. В базе хранится реестр: тип документа, статус, сумма, дата, компания, путь к файлу, письмо отправки и история событий. Telegram-токен и секреты AI API хранятся в Hermes и не попадают в HRM HuntTech.

Бот не сканирует существующий архив с целью изменения файлов актов, договоров, УПД, счетов, заданий, чеков и других деловых документов. Чтение структуры папок допускается только для выбора целевого пути и формирования алиасов, без записи в существующие документы.

### 1.1. Реализация Этапа 2

Этап 2 реализует первый рабочий участок процесса:

```text
Telegram photo/PDF
→ скачивание файла Telegram-ботом
→ AccountingDocumentIngestService
→ Сканы/Входящие/YYYY-MM-DD/
→ AccountingDocument(status = NEW)
→ AccountingDocumentEvent(eventType = RECEIVED)
```

В Этапе 2 бот не выполняет OCR, не просит подтверждение карточкой, не выбирает контрагента, не раскладывает документы по `Договоры/Клиенты/...` и не отправляет письма бухгалтеру. Эти действия остаются в следующих этапах.

Технические настройки входящей папки и разрешенного Telegram user id описаны в [AccountingDocumentIngestService.md](../services/AccountingDocumentIngestService.md).

## 2. Потоки документов

### 2.1. Первичная документация

Типичные документы:

- договор;
- акт;
- УПД;
- счет;
- задание;
- приложение;
- прочее.

Папка назначения:

```text
ХантТек/Договоры/Клиенты/<год>/<контрагент>/
```

Если у контрагента уже есть подпапка `Счета и акты`, акты, счета и УПД помещаются туда:

```text
ХантТек/Договоры/Клиенты/<год>/<контрагент>/Счета и акты/
```

Тема дневного письма:

```text
[YYYY-MM-DD] HRM HuntTech: первичные документы за DD.MM.YYYY
```

Пример:

```text
[2026-07-29] HRM HuntTech: первичные документы за 29.07.2026
```

Периодичность: один раз в день.

### 2.2. Чеки авансового отчета

Чеки не смешиваются с первичкой и отправляются отдельным письмом.

Папка месяца:

```text
ХантТек/Бухгалтерия/Авансовые отчеты/<год>/<MM месяц>/
```

Внутренняя структура месяца:

```text
К отправке/
Отправлено/
Брак/
```

Имя файла:

```text
YYYY-MM-DD <категория> <сумма> <организация>.pdf
```

Примеры:

```text
2026-07-12 топливо 4280.50 Лукойл.pdf
2026-07-18 услуга 1200.00 Яндекс 360.pdf
2026-07-25 связь 950.00 МТС.pdf
```

Тема месячного письма должна содержать фразу `Авансовый отчет`:

```text
[YYYY-MM-DD] HRM HuntTech: Авансовый отчет за <месяц> <год>
```

Пример:

```text
[2026-07-29] HRM HuntTech: Авансовый отчет за июль 2026
```

Периодичность: один раз в месяц в последних числах месяца. После успешной отправки чеки перемещаются из `К отправке` в `Отправлено`.

## 4. Сопоставление со справочниками HRM HuntTech

Новые справочники не должны дублировать существующую модель HRM HuntTech.

| Данные | Решение |
| --- | --- |
| Контрагент / клиент | использовать существующий `Company` |
| Наше юрлицо | использовать существующий `Company` с `ourLegalEntity = true` |
| Валюта | использовать существующий `Currency` |
| Пользователь-отправитель Yandex.Mail | использовать существующий `ExtUser` и его SMTP-настройки |
| Получатели бухгалтерских писем | новый справочник `AccountingRecipient`, потому что бухгалтер может быть внешним контактом без учетной записи HRM HuntTech |
| Договор | опционально связать с существующим `LaborAgreement` |
| Тип документа | enum, не справочник |
| Статус документа | enum, не справочник |
| Поток документа | enum, не справочник |
| Категория чека | новый справочник, потому что список меняется по правилам бухгалтерии |
| Алиасы компаний | новая вспомогательная таблица к `Company`, не отдельный справочник контрагентов |

## 5. Рекомендуемые сущности

### AccountingDocument

Главная запись реестра. Хранит поток, тип документа, статус, даты, сумму, связи с `Company`, `Currency`, опционально `LaborAgreement`, пути в Yandex.Disk и Telegram-метаданные.

Ключевые поля:

- `flowType`;
- `documentType`;
- `status`;
- `receivedAt`;
- `documentDate`;
- `documentNumber`;
- `company`;
- `recognizedCompanyName`;
- `recognizedInn`;
- `amount`;
- `currency`;
- `expenseCategory`;
- `laborAgreement`;
- `originalFileName`;
- `finalFileName`;
- `yandexDiskOriginalPath`;
- `yandexDiskFinalPath`;
- `fileHash`;
- `telegramChatId`;
- `telegramMessageId`;
- `telegramFileId`;
- `confirmedByTelegramUserId`;
- `confirmedAt`;
- `emailBatch`;
- `sentAt`;
- `errorMessage`.

### AccountingEmailBatch

Одна запись соответствует одному письму бухгалтеру. Отправитель берется из `ExtUser`, а получатели выбираются из `AccountingRecipient`. В пакете обязательно хранится фактический снимок адресов, чтобы история старых писем не менялась при замене бухгалтера или изменении его email.

Ключевые поля:

- `flowType`;
- `periodDate`;
- `periodYear`;
- `periodMonth`;
- `status`;
- `subject`;
- `body`;
- `senderUser`;
- `senderEmail`;
- `toEmails`;
- `ccEmails`;
- `bccEmails`;
- `sentAt`;
- `yandexMailMessageId`;
- `errorMessage`.

### AccountingRecipient

Справочник внешних получателей бухгалтерских документов. Не заменяет `ExtUser`: бухгалтер может не быть пользователем HRM HuntTech, а получателей может быть несколько.

Ключевые поля:

- `name`;
- `email`;
- `active`;
- `recipientRole`;
- `flowType`;
- `sendAsTo`;
- `sendAsCc`;
- `sendAsBcc`;
- `comment`.

Рекомендуемые роли:

- `PRIMARY_ACCOUNTANT` — основной бухгалтер;
- `BACKUP_ACCOUNTANT` — резервный бухгалтер;
- `OWNER_COPY` — копия владельцу процесса;
- `OTHER` — другой получатель.

`flowType` определяет, какие письма получает адресат:

- `PRIMARY` — только первичная документация;
- `ADVANCE_REPORT` — только авансовые отчеты;
- `ALL` — оба потока.

### AccountingDocumentEvent

Журнал событий по документу.

Типовые события:

- `RECEIVED`;
- `OCR_PROCESSED`;
- `CONFIRMATION_REQUESTED`;
- `CONFIRMED`;
- `RENAMED`;
- `MOVED_TO_FINAL_FOLDER`;
- `ADDED_TO_EMAIL_BATCH`;
- `SENT`;
- `MOVED_TO_SENT_FOLDER`;
- `REJECTED`;
- `ERROR`.

### AccountingExpenseCategory

Справочник категорий чеков авансового отчета.

Предзаполнить:

- `топливо`;
- `связь`;
- `услуга`;
- `подписка`;
- `ПО / сервис`;
- `такси`;
- `почта`;
- `канцтовары`;
- `госпошлина`;
- `прочее`.

Для категории полезно хранить `matchKeywords`, например для `топливо`: `АЗС`, `Лукойл`, `Газпромнефть`, `бензин`, `дизель`.

### AccountingCompanyAlias

Вспомогательная таблица сопоставления OCR-названий с существующей `Company`.

Поля:

- `company`;
- `alias`;
- `inn`;
- `yandexDiskFolderPath`;
- `active`.

Пример:

```text
ООО РУССКИЕ МЕДИА → Company: Русские Медиа
РУССКИЕ МЕДИА → Company: Русские Медиа
```

## 6. Ошибки и ручные развилки

### Неприкосновенность существующих деловых документов

Бот не изменяет акты, договоры, УПД, счета, задания, чеки и другие деловые файлы, которые существовали на Yandex.Disk или локальном диске до загрузки через Telegram. Запрещены автоматические операции над существующим архивом:

- удаление;
- переименование;
- перезапись;
- перемещение;
- изменение содержимого;
- массовая нормализация структуры.

Если для нового документа целевой файл уже существует, бот должен остановить операцию, сообщить пользователю о конфликте и предложить сохранить новый файл с уникальным именем либо отложить обработку.

### Контрагент не найден

Если бот не нашел контрагента в `Company`, он не создает компанию автоматически и не отправляет документ бухгалтеру.

Поведение:

- документ получает статус `WAITING_COMPANY_MATCH`;
- файл остается в `Сканы/Не разобрано/<дата>/`;
- бот отправляет сообщение: `Контрагент не найден: "<распознанное название>". Что сделать?`;
- доступны действия: выбрать компанию из HRM HuntTech, создать новую компанию после явного подтверждения, добавить алиас к существующей компании, отложить, не отправлять.

Если пользователь выбирает существующую компанию, бот сохраняет алиас и продолжает обработку. Если пользователь создает новую компанию, бот создает минимальную запись `Company` с `ourClient = true` только после явного подтверждения.

### Плохой скан

Документ получает статус `BAD_SCAN`, файл перемещается в папку брака, бухгалтеру не отправляется.

### Дубликат

Если `fileHash` уже был обработан, бот предупреждает пользователя и не добавляет документ в отправку без подтверждения.

### Ошибка отправки письма

Пакет получает статус `ERROR`, документы остаются в состоянии готовности к отправке, а бот присылает ошибку в Telegram. Повторная отправка должна использовать тот же пакет или явно созданный новый пакет с событием отмены старого.

## 7. Предзаполнение данных

Перед запуском процесса нужно проверить или заполнить:

- `Company`: клиенты имеют `ourClient = true`, наше юрлицо имеет `ourLegalEntity = true`;
- `Currency`: есть `RUB`;
- `AccountingRecipient`: минимум один активный получатель для первички и один активный получатель для авансового отчета; это может быть один и тот же бухгалтер с `flowType = ALL`;
- `AccountingExpenseCategory`: минимальный набор категорий чеков;
- `AccountingCompanyAlias`: стартовые алиасы из `Company.comanyName`, `Company.companyShortName` и названий папок Yandex.Disk;
- настройки бухгалтерской автоматизации: пути Yandex.Disk, пользователь-отправитель, Telegram user id для подтверждений, время дневной отправки, правило месячной отправки.

## 8. Границы первого этапа

Первый этап можно реализовать без UI в HRM HuntTech:

- прием файлов через Telegram;
- сохранение в Yandex.Disk;
- запись реестра в HRM HuntTech;
- подтверждение в Telegram;
- раскладка по папкам;
- дневная отправка первички;
- месячная отправка чеков авансового отчета;
- журнал событий.

Экран HRM HuntTech добавляется позже поверх готовых сущностей и не должен менять правила процесса.
