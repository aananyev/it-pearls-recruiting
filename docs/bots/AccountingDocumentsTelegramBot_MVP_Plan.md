# MVP-план бухгалтерского Telegram-бота

> Рабочий план минимально необходимой реализации Telegram-бота HRM HuntTech для первичных документов и чеков авансового отчета. План фиксирует объем первой версии и используется перед созданием будущей ветки разработки.

## Назначение и бизнес-смысл (What & Why)

Первая версия должна убрать ручную рутину: сканирование, переименование, раскладку по папкам Yandex.Disk, контроль отправки бухгалтеру и отдельную отправку чеков авансового отчета.

MVP не пытается сразу сделать полноценный экран HRM HuntTech и полный автопилот. Критичный принцип первой версии: бот готовит действие, но важные решения подтверждаются пользователем в Telegram.

Строго запрещено трогать, удалять, менять, переименовывать, перезаписывать или перемещать уже существующие деловые документы на Yandex.Disk и локальном диске: акты, договоры, УПД, счета, задания, чеки и другие файлы клиентского или бухгалтерского архива. MVP работает только с новыми файлами, отправленными в Telegram-бот и сохраненными ботом во входящую папку.

## UI Context & Navigation

Основной интерфейс MVP — Telegram-бот.

Пользовательские входы:

- отправить фото или PDF документа боту;
- подтвердить или исправить распознанную карточку;
- запросить список документов к отправке;
- вручную запустить отправку, если расписание пропущено;
- отметить документ как плохой скан или не отправлять.

Экран HRM HuntTech в MVP не создается. База HRM HuntTech используется как реестр статусов и событий.

## Behavior Summary

| Действие | Условие | Результат |
| --- | --- | --- |
| Пользователь отправил файл | файл является фото или PDF | файл сохраняется во входящую папку Yandex.Disk, создается запись `AccountingDocument` |
| Бот распознал первичку | найден тип, дата, контрагент или OCR-название | бот отправляет Telegram-карточку подтверждения |
| Бот распознал чек | найдены дата, сумма, организация | бот предлагает категорию и имя файла |
| Пользователь подтвердил документ | все обязательные поля заполнены | файл переименован и перемещен в целевую папку |
| Контрагент не найден | нет совпадения с `Company` или алиасами | документ получает `WAITING_COMPANY_MATCH`, отправка блокируется |
| Наступило время дневной отправки | есть подтвержденная первичка | бот отправляет отдельное письмо бухгалтеру |
| Наступило время месячной отправки | есть чеки в `К отправке` | бот отправляет письмо с фразой `Авансовый отчет` и переносит чеки в `Отправлено` |

## 1. Объем MVP

### 1.1. Входит в MVP

- один Telegram-бот для двух потоков: первичка и авансовые отчеты;
- прием фото и PDF;
- сохранение исходников в Yandex.Disk;
- OCR/AI-распознавание основных реквизитов;
- Telegram-подтверждение перед раскладкой и отправкой;
- раскладка первички по текущей структуре Yandex.Disk;
- раскладка чеков авансового отчета по месячным папкам;
- ежедневная отправка первички через Yandex.Mail;
- месячная отправка авансового отчета отдельным письмом;
- хранение реестра, статусов и событий в HRM HuntTech;
- предзаполненные категории чеков и получатели бухгалтерии;
- блокировка автоматической отправки при неизвестном контрагенте;
- защита от повторной обработки одного и того же файла по hash.

### 1.2. Не входит в MVP

- экран HRM HuntTech для бухгалтерских документов;
- загрузка файлов в CUBA `FileDescriptor`;
- любые изменения уже существующих актов, договоров, УПД, счетов, заданий, чеков и других деловых документов на Yandex.Disk или локальном диске;
- автоматическое создание компаний без подтверждения;
- интеграция с 1С;
- чтение входящей Yandex.Mail-почты;
- сложное согласование несколькими пользователями;
- production-миграция без отдельной команды;
- изменение существующих сущностей HRM HuntTech.

## 2. Этапы реализации

### Этап 0. Подготовка данных и секретов

Результат:

- создан Telegram-бот;
- получен токен бота;
- известен Telegram user id пользователя, который подтверждает документы;
- создан пароль приложения Yandex.Mail;
- утвержден пользователь-отправитель `ExtUser`;
- утвержден список `AccountingRecipient`;
- проверены локальные пути Yandex.Disk.

DoD:

- секреты не попадают в git;
- получатели бухгалтерии согласованы;
- есть тестовая папка Yandex.Disk для dry-run.

### Этап 1. Модель БД и предзаполнение

Результат:

- добавлены новые сущности бухгалтерского контура;
- существующие `Company`, `Currency`, `ExtUser`, `LaborAgreement` не изменены;
- добавлен changelog с preconditions;
- предзаполнены `AccountingExpenseCategory`, `AccountingRecipient`;
- создана таблица `AccountingAutomationSettings`, но секреты, пароли и персональные Telegram ID не предзаполняются;
- `RUB` добавлен только если отсутствовал;
- `AccountingCompanyAlias` создан для будущих ручных подтверждений и dry-run алиасов без автоматического массового заполнения.

DoD:

- повторный запуск миграции не создает дубли;
- SQL не содержит `DROP`, `DELETE`, `TRUNCATE`;
- Hermes проверяет миграцию на копии БД перед production.

### Этап 2. Telegram-прием и реестр

Результат:

- бот принимает фото/PDF;
- сохраняет исходник в `ХантТек/Сканы/Входящие/<дата>/`;
- создает `AccountingDocument`;
- пишет событие `RECEIVED`;
- рассчитывает `fileHash`;
- определяет поток: `PRIMARY` или `ADVANCE_REPORT`, если возможно.

DoD:

- невалидный файл получает понятное сообщение;
- дубль не проходит молча;
- запись документа можно найти в БД.

### Этап 3. Распознавание и подтверждение

Результат:

- бот извлекает тип документа, дату, номер, сумму, контрагента или организацию чека;
- сопоставляет контрагента через `Company` и `AccountingCompanyAlias`;
- отправляет Telegram-карточку с кнопками;
- поддерживает ручные исправления основных полей.

DoD:

- неизвестный контрагент переводит документ в `WAITING_COMPANY_MATCH`;
- пользователь может выбрать существующую компанию;
- после выбора компании создается алиас;
- плохой скан переводится в `BAD_SCAN` и не отправляется.

### Этап 4. Раскладка файлов

Результат:

- первичка переименовывается и перемещается в `Договоры/Клиенты/<год>/<контрагент>/`;
- акты, счета и УПД используют подпапку `Счета и акты`, если она есть или должна быть создана;
- чеки попадают в `Бухгалтерия/Авансовые отчеты/<год>/<MM месяц>/К отправке/`;
- пути сохраняются в `AccountingDocument`.

DoD:

- исходный и финальный путь зафиксированы;
- при ошибке перемещения документ получает `ERROR`;
- повторная операция не ломает уже перемещенный файл.

### Этап 5. Отправка писем

Результат:

- ежедневная отправка первички отдельным письмом;
- месячная отправка чеков авансового отчета отдельным письмом;
- тема первички: `[YYYY-MM-DD] HRM HuntTech: первичные документы за DD.MM.YYYY`;
- тема авансового отчета содержит `Авансовый отчет`;
- `AccountingEmailBatch` хранит `senderEmail`, `toEmails`, `ccEmails`, `bccEmails`, тему и результат;
- после успешной отправки чеки перемещаются в `Отправлено`.

DoD:

- первичка и авансовые отчеты не смешиваются;
- пустое письмо не отправляется;
- ошибка Yandex.Mail фиксируется в `AccountingEmailBatch` и Telegram;
- повторная отправка требует явного действия или корректного retry.

### Этап 6. Команды контроля в Telegram

Результат:

- `/status` — краткий статус очередей;
- `/pending` — документы на подтверждении;
- `/ready` — документы к отправке;
- `/send_today` — ручная отправка первички за день;
- `/send_advance_report` — ручная отправка авансового отчета за месяц;
- `/errors` — документы с ошибками.

DoD:

- команды доступны только разрешенному Telegram user id;
- ответы не раскрывают секреты;
- ручные отправки пишут события в журнал.

## 3. Минимальный набор сущностей MVP

## 5. Риски MVP

| Риск | Снижение риска |
| --- | --- |
| Бот случайно меняет существующий архив актов, договоров или чеков | запрет записи в существующие деловые файлы; работа только с bot-managed входящими файлами |
| OCR неверно распознал контрагента | обязательное Telegram-подтверждение и алиасы |
| Бот отправил документ не туда | статус `WAITING_CONFIRMATION` до раскладки |
| Дубль документа | `fileHash` и предупреждение |
| Смешались первичка и чеки | разные `flowType`, папки, расписания и письма |
| Сломалась отправка Yandex.Mail | batch получает `ERROR`, документы остаются к отправке |
| Production-миграция внесла лишние данные | обязательный dry-run, backup, копия БД и Hermes |

## 6. Критерии готовности MVP

MVP считается реализованным, если:

- документ можно отправить боту и увидеть карточку подтверждения;
- первичка после подтверждения попадает в правильную папку Yandex.Disk;
- чек после подтверждения попадает в `К отправке`;
- ежедневное письмо первички отправляется бухгалтеру;
- месячное письмо авансового отчета отправляется отдельно;
- после отправки чеки перемещаются в `Отправлено`;
- в HRM HuntTech сохраняются статусы, пути, batch и события;
- неизвестный контрагент блокирует отправку до ручного выбора;
- повторный запуск миграции и отправки не создает дубли;
- Hermes проверил точный HEAD перед production-миграцией.
