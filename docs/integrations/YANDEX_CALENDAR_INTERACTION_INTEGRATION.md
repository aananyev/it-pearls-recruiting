# Интеграция взаимодействий с кандидатами с Яндекс Календарём (CalDAV)

## 1. Назначение и бизнес-смысл (What & Why)

Функционал обеспечивает автоматическую и ручную синхронизацию встреч по кандидатам из формы создания/редактирования взаимодействия (`IteractionListEdit`) в персональные и корпоративные Яндекс Календари (Яндекс 360) по протоколу CalDAV.

## 2. Связи в интерфейсе и навигация (UI Context & Navigation)

- Пользователь настраивает персональное подключение в `ExtSettingsWindow` на вкладке «Яндекс-360».
- Администратор ведёт корпоративные календари через «Администрирование» → «Корпоративные Яндекс Календари».
- `IteractionListEdit` использует доступные календари при создании или изменении взаимодействия с кандидатом.

## 3. Краткий обзор бизнес-логики поведения (Behavior Summary)

- Проверка подключения → CalDAV discovery возвращает `207 Multi-Status` → подключение отмечается активным, отображается фактическое число календарей.
- Проверка подключения → Яндекс возвращает `401`, `403`, `404` или происходит сетевой сбой → подключение отмечается неактивным, фиктивные пути календарей не создаются.
- Сохранение взаимодействия с включённой синхронизацией → выбран календарь и авторизация действительна → событие создаётся или обновляется по стабильному UID.
- Снятие флага синхронизации → ранее созданное событие известно → выполняется удаление только этого события.

## 4. Официальный протокол и требования Yandex 360

### Источники

- [Сервисные приложения Yandex 360](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications) — OAuth, временные пользовательские токены, CalDAV endpoint и примеры `PUT`/`GET` событий.
- [Справочник ServiceApplicationsService_Create](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Create) — допустимые календарные scopes и коды `401`, `403`, `404`.
- [Реализация OAuth в Яндексе](https://yandex.ru/dev/id/doc/ru/concepts/ya-oauth-intro) — состав токена, жизненный цикл и отзыв доступа.
- RFC 4791 (CalDAV) и RFC 5545 (iCalendar) — discovery/query и формат `VEVENT`.

### Сопоставление с HRM HuntTech

| Требование | Официальный контракт | Реализация HRM HuntTech |
|---|---|---|
| Endpoint событий | `https://caldav.yandex.ru/calendars/<user_email>/<calendar>/<uid>.ics` | Базовый URL `https://caldav.yandex.ru`, путь календаря хранится отдельно |
| Авторизация | `Authorization: OAuth <token>` | Заголовок формируется в `sendHttp`; токен хранится только зашифрованным |
| Права | Для полного CRUD: `calendar:all` либо достаточный набор `calendar:events.read/write` и `calendar:calendars.read` | Scope не хранится; фактические права проверяются ответами CalDAV (`401/403`) |
| Поиск календарей | CalDAV principal / calendar-home-set | `PROPFIND` principal (`Depth: 0`) и home set (`Depth: 1`) |
| Чтение | CalDAV `REPORT`/`GET` | `REPORT calendar-query`, fallback `PROPFIND`, read-back `GET` |
| Создание/изменение | `PUT .../<uid>.ics`; `201` при создании | `PUT`, успешными считаются `200/201/204`; один UID обеспечивает update |
| Удаление | CalDAV `DELETE` конкретного ресурса | `DELETE .../<uid>.ics`; успешны `200/204` |
| Organization/user ID | Нужны только для сервисного приложения и token exchange | Текущий персональный режим их не использует; пользователь определяется OAuth-токеном и email |

Для централизованного доступа администратора требуется отдельная архитектура сервисного приложения: `org_id`, ClientID/secret, разрешённые scopes и краткоживущий пользовательский токен (официально — 1 час). Текущий персональный режим HRM HuntTech не следует ошибочно описывать как IAM-интеграцию.

## 6. Модель данных

### Сущность `CorporateYandexCalendar` (`hunttech_CorporateYandexCalendar`)
Таблица: `HUNTTECH_CORP_YANDEX_CAL`
- `name` (String, not null, 255) — отображаемое название (например: «Рекрутинг HuntTech»);
- `calendarPath` (String, not null, 512) — путь к календарю (например: `/calendars/hr@hunttech.ru/events/`);
- `accountEmail` (String, 255) — сервисный или корпоративный email аккаунта;
- `calendarBaseUrl` (String, 512, default `https://caldav.yandex.ru`) — базовый CalDAV URL;
- `isDefault` (Boolean, default `false`) — признак календаря по умолчанию;
- `active` (Boolean, default `true`) — признак активности;
- `description` (String, 1024) — примечание/описание;
- `oauthTokenEncrypted` (String, 4096) — зашифрованный токен доступа к корпоративному календарю.

### Расширение сущности `IteractionList` (`hunttech_IteractionList`)
- `calendarEventId` (String, 255) — внешний UID события в Яндекс Календаре;
- `calendarId` (String, 512) — путь к выбранному календарю;
- `calendarSyncState` (String, 50) — статус синхронизации (`SYNCED`, `FAILED`, null);
- `addToCalendar` (Boolean, default `false`) — признак необходимости добавления в календарь.

## 7. Алгоритм вычисления календаря по умолчанию

В методе `YandexIntegrationService.getAvailableCalendars(userId)`:
1. **Персональный календарь пользователя**, если он явно настроен в `UserYandexConfiguration` (указан `personalCalendarPath`);
2. **Иначе корпоративный календарь**, назначенный администратором как `isDefault = true`;
3. **Иначе первый доступный активный календарь**;
4. Если календарей нет — список пуст, выбор отсутствует.

В контроллере `CorporateYandexCalendarEdit` при сохранении календаря с `isDefault = true` автоматически снимается признак дефолта с остальных записей, гарантируя уникальность дефолтного корпоративного календаря.

## 8. Поведение экранных форм

### `CorporateYandexCalendarBrowse` и `CorporateYandexCalendarEdit`
- Доступен в главном меню («Администрирование» $\rightarrow$ «Корпоративные Яндекс Календари»).
- Экран редактирования выполнен по стандарту `Edit`:
  * Левый сайдбар `width="312px"` со сводкой статуса (Активен/Отключен, По умолчанию: Да/Нет);
  * Правая рабочая область с карточками основных параметров и параметров интеграции.
  * Фильтрация таблицы защищена от нежелательного раскрытия зашифрованных токенов.

### `IteractionEdit` (Настройка типов взаимодействий)
- Сайдбар приведен к проектному стандарту `width="312px"`.
- Радиокнопка типа дополнительного значения переименована: `"Data"` $\rightarrow$ `"Дата и время (для встреч и Яндекс Календаря)"`.
- Добавлен поясняющий блок с подсказкой для администратора о том, что выбор типа «Дата и время» активирует календарный сценарий при заведении взаимодействия.

### `IteractionListEdit` (Создание/редактирование взаимодействия)
- Блок календаря (`calendarBox`) располагается в правой рабочей части формы непосредственно под полем `addDate`.
- Блок отображается **только тогда**, когда для выбранного типа взаимодействия требуется дата/время (`addDate.isVisible() == true`).
- Контролы:
  * `addToCalendarCheckBox` («Добавить в календарь»);
  * `calendarLookupField` («Календарь») с человекочитаемыми именами.
- Ленивая загрузка: обращение за календарями выполняется только при открытии календарного сценария.
- Если календарей нет: чекбокс отключается с подсказкой «Нет доступных календарей», форма сохраняется штатно.
- При сохранении взаимодействия:
  * Взаимодействие фиксируется в БД;
  * После коммита вызывается синхронизация CalDAV;
  * В случае сетевой или API-ошибки Яндекса взаимодействие не теряется, пользователю выводится деликатное предупреждение: *«Взаимодействие сохранено, но событие не удалось добавить в Яндекс Календарь.»*;
  * При успешной синхронизации выводится toast-уведомление *«Событие успешно синхронизировано с Яндекс Календарём.»*.

## 9. Формирование события и TimeZone

- **Заголовок встречи**: формируется по шаблону `<Имя кандидата> — <Должность кандидата> — <Название взаимодействия>`. При отсутствии отдельных параметров формируется корректный заголовок без `null`.
- **Длительность**: 1 час от указанного времени взаимодействия (`addDate`).
- **Таймзона**: берется из сессии текущего пользователя (`userSession.getTimeZone().getID()`) или настроек Саратовского времени (`Europe/Saratov`), исключая смещения времени.
- **Идемпотентность**: при повторном сохранении взаимодействия CalDAV получает тот же `eventUid`, обновляя существующее событие.
- **Отмена и перенос**: при снятии галочки событие удаляется из календаря; при смене календаря событие безопасно переносится в новый календарь.

## 10. Диагностика и автоматизированные проверки

`YandexCalendarConnectionDiagnosticsTest` использует транспортный дубль без внешней сети и реальных секретов. Проверяются:

- `207 Multi-Status` и корректный discovery;
- `401` — недействительный или истёкший OAuth-токен;
- `403` — отсутствующий календарный scope или иное ограничение прав;
- `404` — недоступная учётная запись/principal/calendar home;
- timeout/сетевая ошибка — `503` без утечки токена или тела ответа;
- отрицательный результат сбрасывает `calendarConnected` и фиксирует время проверки.

CRUD-проверка на production запрещена. Интеграционный CRUD допускается только в тестовом контуре и отдельном календаре: создать уникальный `UID`, прочитать его, обновить тем же `UID`, удалить конкретный `.ics`, затем обязательным `GET` подтвердить отсутствие ресурса. Cleanup выполняется в `finally`; реальные события пользователя не используются.
