## Цель

Продолжить поэтапную оптимизацию открытия `JobCandidateEdit` без изменения функциональности, бизнес-логики, состава экранных элементов и результата сохранения данных.

До начала изменений провести инструментальное профилирование актуального состояния и выбрать только один следующий наиболее тяжёлый блок первоначальной загрузки. Не объединять несколько оптимизаций в один этап.

## Обязательные ограничения

1. Не изменять уже одобренную реализацию Stage 1–3 без доказанной регрессии.
2. Не менять бизнес-логику, права доступа, валидацию, порядок сохранения и пользовательский результат.
3. Не удалять поля, вкладки, таблицы, действия и данные из формы.
4. Не допускать `detached object`, `Cannot get unfetched attribute`, `OutOfMemoryError`, N+1 и повторных загрузок.
5. Код этапа и итоговый отчёт коммитить отдельно.
6. При регрессии выставлять `NO-GO` и не переходить дальше.

## Порядок выполнения

### 1. Baseline

На точном SHA `fe25c45183537cf89a43f2bb396ff747a264c66a` зафиксировать:

- время открытия `JobCandidateEdit` минимум в пяти повторах;
- медиану и среднее значение;
- число SQL-запросов при первоначальном открытии;
- наиболее долгие запросы;
- heap до открытия и после открытия формы;
- время обработки ключевых lifecycle-методов, загрузчиков и подписчиков событий;
- используемого тестового кандидата и параметры окружения.

### 2. Выбор объекта Stage 4

По результатам профилирования выбрать один блок с максимальной измеренной стоимостью, который можно безопасно исключить из первоначальной загрузки или загружать по требованию.

В отчёте до изменения указать:

- название свойства, контейнера, loader, метода или вкладки;
- фактическую стоимость в миллисекундах;
- число SQL-запросов;
- объём загружаемых данных;
- почему перенос безопасен;
- почему он не меняет бизнес-логику.

### 3. Реализация

Внести минимальные изменения только для выбранного блока. Использовать существующую архитектуру progressive/lazy loading, если она применима. Добавить понятные комментарии на русском языке к изменяемому коду и актуализировать living documentation проекта.

### 4. Проверки

На итоговом SHA кода выполнить:

- чистую сборку `clean assemble`;
- релевантные unit- и integration-тесты;
- деплой в Tomcat;
- HTTP 200 для `/hrm/`;
- функциональный smoke-test через UI;
- открытие существующего кандидата;
- проверку всех основных вкладок;
- первое и повторное открытие целевой вкладки;
- изменение допустимого тестового значения;
- сохранение, закрытие и повторное открытие кандидата;
- проверку сохранности данных.

### 5. SQL-доказательства

Представить SQL-лог, доказывающий:

- отсутствие выбранного тяжёлого блока при первоначальном открытии формы;
- контролируемую загрузку при первом обращении;
- отсутствие повторной загрузки при повторном переключении;
- отсутствие N+1;
- отсутствие лишних запросов после сохранения.

### 6. Анализ исключений

Проверить логи минимум на:

- `IllegalStateException`;
- `Cannot get unfetched attribute`;
- `detached object`;
- `OutOfMemoryError`;
- `NullPointerException`;
- ошибки `DataContext.merge`;
- ошибки сохранения;
- новые `WARN` и `ERROR`.

### 7. Сравнительные замеры

Использовать того же кандидата и то же окружение. Выполнить минимум пять повторов до и после. Привести:

- среднее и медиану времени открытия;
- процент изменения;
- число SQL-запросов;
- время первого обращения к вынесенному блоку;
- поведение при повторном обращении;
- изменение heap.

## Критерий GO

`GO` разрешён только если одновременно выполнено всё:

- протестирован точный итоговый SHA;
- сборка и тесты успешны;
- приложение отвечает HTTP 200;
- функциональный smoke-test успешен;
- сохранение работает;
- SQL подтверждает ленивую загрузку;
- N+1 и повторные загрузки отсутствуют;
- новых исключений нет;
- производительность первоначального открытия не ухудшилась;
- бизнес-логика и функциональность не изменены.

После отчёта остановиться и не начинать Stage 5 без отдельного одобрения.
