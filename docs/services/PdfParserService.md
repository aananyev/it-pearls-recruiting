# PdfParserService — разбор PDF и навыков в HRM HuntTech

## Назначение и Бизнес-смысл (What & Why)

`PdfParserService` извлекает текст и изображения из PDF-файлов и определяет навыки, упомянутые в резюме кандидата или описании вакансии. Результат используется не только для визуального блока навыков в `JobCandidateEdit`, но и для пересканирования `CandidateCV.skillTree`, поиска кандидатов по навыкам и расчёта соответствия резюме вакансии.

Критичное требование сервиса — одновременно сохранять бизнес-контракт `List<SkillTree>` и не передавать между core- и web-слоями полный persistence-граф всего справочника. Нарушение первого требования ломает сохранение навыков резюме; нарушение второго может исчерпать Java heap при открытии карточки кандидата.

## Связи в интерфейсе и Навигация (UI Context & Navigation)

Сервис вызывается из следующих сценариев:

- `JobCandidateEdit` → фоновый анализ последнего резюме после отображения формы;
- фрагмент `Skillsbar` → формирование визуальных меток навыков;
- `CandidateCVEdit` → пересканирование резюме и сохранение списка `CandidateCV.skillTree`;
- `FindSuitable` и `Suggestjobcandidate` → сравнение резюме и вакансий;
- `OpenPositionEdit` → анализ описания вакансии и заполнение навыков;
- операции извлечения текста и изображений из PDF.

Пользователь непосредственно не открывает сервис. Он видит результат в карточках кандидата, резюме и вакансии.

## Краткий обзор бизнес-логики поведения (Behavior Summary)

- Пустой входной текст → сервис возвращает пустой список → вызывающий экран продолжает работу без исключения.
- Поиск совпадений → весь справочник читается скалярной JPQL-проекцией → Entity-граф справочника не создаётся.
- Найден навык → его ID и допустимый родитель добавляются в упорядоченный набор → дубликаты родителя исключаются.
- `notParsing = false` → навык разрешён к распознаванию → совпадение участвует в результате.
- `notParsing = true` или `null` → запись пропускается → сохраняется прежняя семантика HRM HuntTech.
- Пустой ID или `skillName` → запись пропускается → в лог пишется агрегированное предупреждение без серии stack trace.
- После отбора ID → загружаются только найденные реальные сущности через узкий view → вызывающие экраны могут безопасно отображать и сохранять `SkillTree`.

## API

```java
List<SkillTree> parseSkillTree(String inputText);
```

Публичная сигнатура и смысл результата сохранены. Метод возвращает штатные сущности `SkillTree`, загруженные `DataManager`, а не искусственно созданные объекты с существующими ID.

Для найденных сущностей используется `skillTree-edit-view`, содержащий поля, необходимые существующим сценариям:

- `skillName`;
- `wikiPage`;
- `styleHighlighting`;
- `notParsing`;
- `prioritySkill`;
- `comment`;
- непосредственный родитель `skillTree`;
- `specialisation`;
- `fileImageLogo`.

В результат не загружаются обратные коллекции всех кандидатов, вакансий и резюме. Количество возвращаемых сущностей ограничено фактическими совпадениями в анализируемом тексте.

## Алгоритм безопасной загрузки

1. `DataManager.loadValues()` читает только ID, название, `notParsing` и данные непосредственного родителя.
2. Входной текст нормализуется один раз через `Locale.ROOT`.
3. Отбираются только записи с явным `notParsing = false`.
4. Идентификаторы сохраняются в `LinkedHashSet` в порядке «найденный навык → родитель».
5. По отобранным ID выполняется второй JPQL-запрос с `skillTree-edit-view`.
6. Загруженные сущности упорядочиваются согласно списку ID и возвращаются вызывающему коду.

Такой подход сохраняет полноценные Entity для `DataContext`, но исключает сериализацию всего справочника и его обратных связей.

## Причина и устранение OutOfMemoryError

Проблемный сценарий выполнял анализ навыков при открытии `JobCandidateEdit` и передавал результат core-сервиса в web-слой. При чрезмерном Entity-графе CUBA сериализовала большой объектный набор через `ObjectOutputStream`, после чего `ByteArrayOutputStream` завершался ошибкой:

```text
java.lang.OutOfMemoryError: Java heap space
```

Дополнительную нагрузку создавали повторяющиеся `NullPointerException` для записей с пустыми полями.

Текущая защита состоит из двух независимых уровней:

- `JobCandidateEdit` запускает анализ после отображения формы в `BackgroundTask`;
- `PdfParserServiceBean` возвращает только найденные сущности, предварительно отобранные скалярным запросом.

Увеличенный heap и heap dump являются диагностической страховкой, а не заменой ограничения объектного графа.

## Совместимость сохраняющих сценариев

Результат `parseSkillTree()` записывается в `CandidateCV.skillTree` в нескольких экранах. Поэтому запрещено возвращать transient-снимки `new SkillTree()` с существующими ID: такие объекты не имеют штатного persistence-состояния и могут нарушить merge или отображение полей `specialisation`, `wikiPage` и логотипа.

Безопасный контракт: результат должен состоять только из сущностей, полученных через `DataManager`.

## Автотесты

Файл:

```text

```

Проверяются:

- пустой и `null`-текст;
- пропуск некорректных записей;
- исключение `notParsing = true`;
- сохранение прежнего поведения `notParsing = null`;
- порядок «навык → родитель»;
- дедупликация общего родителя;

  --stacktrace

## Эксплуатационные ограничения

- Анализ навыков в `JobCandidateEdit` выполняется только после отображения формы, не в синхронном `onBeforeShow`.
- Полный текст `CandidateCV.textCV` загружается только для последнего резюме и только для фонового анализа.
- Нельзя заменять скалярный первый этап на загрузку полного списка Entity.
- Нельзя возвращать искусственные `SkillTree` с существующими ID.
- View второго этапа не должен включать обратные коллекции `candidates`, `openPosition` и `candidateCV`.
- Изменение правила `notParsing` требует отдельного бизнес-решения и миграции данных.
