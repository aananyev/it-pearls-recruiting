# ExtSettingsWindowMainBackground — настройка фона главного экрана

> Screen ID: `settings`.  
> Контроллер: `ExtSettingsWindowMainBackground`.  
> Базовая цепочка: `ExtSettingsWindowInterfaceLayout` → `ExtSettingsWindowEmailNavigation` → `ExtSettingsWindow`.

## Назначение и бизнес-смысл (What & Why)

Расширение позволяет пользователю HRM HuntTech выбрать персональное фоновое изображение главного экрана либо вернуться к случайному системному фону активной темы. Настройка должна давать немедленную и однозначную обратную связь: открывать штатный выбор файла, показывать имя загруженного изображения и явно сообщать, какой режим будет сохранён.

## UI Context & Navigation

Экран открывается как `SettingsWindow`. Требуемый путь: вкладка «Интерфейс» → пункт левой навигации «Фон главного экрана» → карточка выбора фона. Нажатие пункта переводит фокус к `mainScreenBackgroundUpload`; другие вкладки и блоки SettingsWindow не изменяются.

## Behavior Summary

- открытие → читается текущий `UserSettings.fileImageFace` → показывается сохранённый пользовательский либо системный режим;
- «Выбрать изображение» → нажата реальная кнопка `FileUploadField` → открывается системный file chooser;
- выбор PNG/JPG/JPEG/WEBP до 15 МБ → загрузка завершилась успешно → descriptor маркируется `hrm-main-background-`, исходное имя сохраняется в суффиксе, ссылка записывается в редактируемый datasource;
- успешная загрузка → `showFileName=true` → имя загруженного файла отображается рядом с кнопкой;
- ошибка загрузки → успешное событие не получено → datasource и режим не меняются, показывается предупреждение;
- пользовательского фона нет → статус `Используется случайный фон активной темы.`;
- пользовательский фон успешно загружен → статус `Используется пользовательский фон.`;
- «Использовать системные фоны» → ссылка очищается только в редактируемом datasource → статус переключается на системный режим;
- «ОК» → выполняется штатная commit-цепочка → фон сохраняется, а только неиспользуемые маркированные фоновые файлы удаляются;
- «Отмена» → пользователь выбирает «Остаться» либо «Выйти без сохранения» → загрузка или очистка не сохраняется в `UserSettings`;
- entity, БД, Liquibase, `views.xml`, JPQL и механизм `HrmMainScreen` не меняются.

## Контракт Upload

`mainScreenBackgroundUpload` остаётся самостоятельным `FileUploadField` без `datasource`/`property`: контроллер связывает descriptor с `UserSettings.fileImageFace` только после `FileUploadSucceedEvent`. Это сохраняет управляемый сценарий «ОК/Отмена».

XML-контракт:

- `fileStoragePutMode="IMMEDIATE"`;
- `uploadButtonCaption="Выбрать изображение"` — подпись реальной Vaadin-кнопки, а не caption внешнего layout;
- `showFileName="true"`;
- `height="36px"` и `width="100%"` — ненулевая интерактивная область;
- `accept="*.png,*.jpg,*.jpeg,*.webp"`;
- `permittedExtensions=".png,.jpg,.jpeg,.webp"`;
- `fileSizeLimit="15728640"`;
- `showClearButton="false"`, поскольку очистка выполняется отдельной бизнес-кнопкой;
- локальные SCSS не используют `pointer-events` и не скрывают `.v-upload`.

Статус обновляется после успешной загрузки, при открытии формы и после явной очистки. Простое открытие file chooser и ошибка загрузки не переводят форму в пользовательский режим.

## Очистка и файловая безопасность

`clearMainScreenBackground()` устанавливает `fileImageFace` в `null` только в редактируемом datasource. Физическое удаление выполняется после успешного commit и только для descriptor, имя которого начинается с `hrm-main-background-`. Legacy-фотографии и другие файлы пользователя не удаляются. Выход без сохранения не запускает cleanup.

## Контракт кнопок

### ОК

Выполняются действующая валидация и `super.commit()`. Флаг `successfulCommitClosing` подавляет повторный диалог несохранённых изменений только во время успешного закрытия. После commit удаляются лишь неиспользуемые маркированные фоновые файлы.

### Отмена

Показывается вопрос `Остаться в экране или выйти без сохранения?` с действиями `Остаться` и `Выйти без сохранения`. Второе использует штатный CUBA `closeWithDiscard()` и не выполняет commit.

## Проверки Hermes

Hermes проверяет точный HEAD ветки и PR в `master`, затем выполняет:

1. `git diff --check`;
2. компиляцию web и core tests;
3. `MainScreenBackgroundContractTest` — ожидается `10/10 PASS`;
4. `ScreenViewIntegrityTest` — ожидается `8/8 PASS`;
5. сборку SCSS семи тем;
6. `clean assemble` — ожидается `BUILD SUCCESSFUL`;
7. чистый local deploy и `/hrm/` = HTTP 200;
8. browser smoke в новом сеансе: открытие file chooser, имя файла, оба статуса, повторное открытие формы, «ОК», очистка и оба действия «Отмена»;
9. отсутствие ошибок Upload, FileStorage, `FileDescriptor`, Vaadin RPC и connector в Tomcat logs.

Source-contract тест подтверждает конфигурацию и порядок вызовов, но фактическое открытие системного file chooser подтверждается только browser smoke Hermes.
