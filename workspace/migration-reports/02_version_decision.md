## 4. Технические ограничения

### Java
- CUBA 7.3 требует Java 11
- Jmix 2.x+ требует Java 17+
- **Действие:** Переход на Java 17 (Corretto 17 доступен) или Java 21 LTS

### Jakarta vs Javax
- CUBA 7.3 использует Javax (CUBA абстрагирует)
- Jmix 2.8 уже на Jakarta EE 10
- Зависимость проекта от `jakarta.mail:jakarta.mail-api:2.1.2` — уже частично на Jakarta
- **Действие:** Автоматическая конвертация `javax.*` → `jakarta.*` при миграции

### UI: Vaadin 8 (CUBA Generic UI) → Vaadin 24 (Jmix Flow UI)
- Полная переработка: XML-дескрипторы CUBA → аннотации/Java Flow UI
- Кастомные Vaadin 8 компоненты требуют портирования на Vaadin 24
- Миграция через Jmix Studio — частично автоматизирована
- **Действие:** Ручная переработка + Jmix Studio (рекомендуется после создания target-проекта)

### DBMS
- Стабильный PostgreSQL 11
- Миграция через Liquibase (Jmix) — стандартная процедура
- **Действие:** Backup → staging → Liquibase → data migration скрипты

## 5. Финальное решение

### Путь: CUBA 7.3 → Jmix 2.8 LTS → Jmix 3.0

| Этап | Действие | Версия |
|---|---|---|
| **1** | Создание Jmix-проекта (Jmix 2.8.2 LTS) | Jmix 2.8.2 |
| **2** | Перенос кода: entities, services, бизнес-логика | Jmix 2.8.2 |
| **3** | Перенос UI (CUBA Generic UI → Flow UI) | Jmix 2.8.2 |
| **4** | Перенос безопасности | Jmix 2.8.2 |
| **5** | Миграция данных в Jmix 2.8 | Jmix 2.8.2 |
| **6** | Тестирование и валидация | Jmix 2.8.2 |
| **7** | **Upgrade Jmix 2.8 → Jmix 3.0** | Jmix 3.0.0 |
| **8** | Финальное тестирование | Jmix 3.0.0 |
| **9** | Cutover на production | Jmix 3.0.0 |

### Обоснование

1. **Безопасность:** документированный путь миграции для CUBA 7.2 → Jmix 2.x
   содержит готовые Gradle-задачи, CLI-инструменты и AI-шаблоны.
2. **Предсказуемость:** upgrade 2.x → 3.x — стандартная процедура Jmix.
3. **Время:** двухэтапность добавляет ~1-2 недели на upgrade, но экономит месяцы
   на отладке неподдерживаемого migration path.
4. **Долгосрочная цель:** Jmix 3.0 с Jakarta EE 10, Spring Boot 3.x,
   современной архитектурой.

### Альтернатива (если будет принято решение рискнуть)

Если будет принято решение идти напрямую на Jmix 3.0:
- Провести эксперимент: создать тестовый Jmix 3.0 проект, попробовать
  применить migration tooling. Если успешно — перепланировать.
- В отчёте `09_next_steps.md` будет описана процедура проверки.
